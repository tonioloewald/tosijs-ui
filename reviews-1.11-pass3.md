## 🚫 BLOCKER (1)

### B1 — Editable numeric cells silently drop the decimal point and the minus sign, committing a wrong number as valid

`src/data-table.ts:2024` · lens: correctness · **CONFIRMED** (reproduced twice, independently, in headless Chromium against the committed `docs/` build)

Click a `price` cell in the shipped `/data-table/` "Editing" example and type `19.95` at 50/150/250 ms per keystroke → the model commits **95**. `1.5` → **5**. `0.5` → **5**. `-4` in `qty` → **4**. Text cells are unaffected. Every commit fires `change` with `error: null`, so nothing anywhere reports that a digit was lost.

Root cause confirmed by instrumenting the cell's `value` setter, not inferred:

```
input "1"   → SET "1"
input "19"  → SET "19"
input ""    → SET ""    ← the "." keystroke: "19." sanitizes to "", and the
input "9"   → SET "9"      binding writes "" back into the FOCUSED input
input "95"  → SET "95"
```

`buildEditableCell` uses two-way `bindValue: '^.<prop>'`; tosijs's delegated listener writes the model on every `input`, and for `<input type=number>` an intermediate `"19."` / `"-"` sanitizes to `""` per the HTML value-sanitization algorithm. The binding's `toDOM` then wipes the prefix the user already typed. A bare `<input type=number>` on the same page accepts `12.5` normally, so this is the binding, not the browser. The same wipe applies to any input type with a sanitization step (`date`, `datetime-local` cells built from `format`).

**Why every lane is green:** `tests/table-edit.pw.ts:62,96` and the inline doc test at `src/data-table.ts:565` all assign `.value` programmatically and dispatch a synthetic `change`; `page.keyboard.type()` with no delay never lets a frame run.

**Fix:** stop using two-way `bindValue` for editable cells. Bind for display only and skip the write when the element is `document.activeElement` — exactly what `<tosi-schema-form>.syncValues()` already does, which is why the form is immune (verified: typing `42` into `age` at 150 ms/char works). Keep `handleCellChange` as the sole model write; that also makes the documented "commits on `change`, not on `input`" true of the _model_ and not only of the event. Add a Playwright case that types a decimal **with a per-character delay** — a 0 ms type cannot reproduce it.

Scope is confined to `<tosi-table editable>` (`bindValue` on an input appears only there, plus the enum `select` at :2006 which has no sanitization, and two non-form demos) — but that is the feature this release leads with (`fc23a509`, new since v1.10.2), so it is shipping broken rather than being a pre-existing wart.

## Confirmed majors — fix before tagging

Correctness/security first. All nine are adversarially verified.

**M1 · `change.detail.oldValue` is `undefined` for every cell edit after the first in one focus session** — `src/data-table.ts:1914` _(merged: correctness + dx)_
`_editStart` is seeded only in `handleCellFocus` and `delete`d on every commit. A checkbox clicked three times emits `[{old:true,new:false},{old:undefined,new:true},{old:undefined,new:false}]`; the shipped demo visibly prints `undefined → true`. Worse than first reported: the `delete` happens **before** the `newValue === oldValue` guard, so (a) a no-op commit wipes the baseline for the next real edit, and (b) clearing a numeric cell as the _second_ commit gives `newValue === undefined === stale oldValue` → early return, so **no `change` fires at all and the `item[prop] = newValue` coercion write is skipped**, leaving a schema-typed integer holding the raw string `""`. One-line fix: `this._editStart.set(el, newValue)` instead of `.delete(el)`.

**M2 · The documented `setSchemaValidator` recipe omits `unenforcedKeywords`, so every ESM adopter's forms falsely label validated keywords as unvalidated** — `src/schema-form/validator.ts:113`, `:75`, `src/schema-form.ts:96`, `src/schema-form/unenforced.ts:20`, `CHANGELOG.md:31` _(merged: dx + blast-radius)_
Live repro against the installed `tosijs-schema@1.8.0`: with the documented `setSchemaValidator({ validate, inferSchema })`, `unenforcedKeywords({type:'number', exclusiveMinimum:0, oneOf:[…]})` → `"exclusiveMinimum and oneOf are not validated"`, while `validate()` returns `false` for both — they _are_ enforced. Adding the third function returns empty. The local `ENFORCED` set self-documents as mirroring **1.7.0** and omits `oneOf`/`exclusiveMinimum`/`exclusiveMaximum` — the exact gap tosijs-schema#8 fixed and the reason this release's floor moved to `^1.8.0`. The only correct call site is `src/index-iife.ts:29`, i.e. the doc site renders correctly and the failure is visible **only** to the audience the docs instruct. The console warning users are actually shown prints the defective recipe. The doc page's own headline example uses `exclusiveMinimum` and `oneOf`. Failure direction is fail-safe (over-warning, not a false green), which is why it is not a blocker. Fix: add `unenforcedKeywords` to all three snippets + CHANGELOG, add the three keywords to `ENFORCED`, and correct the stale `// optional peer, ^1.7.0` comment on the same line. Consider asserting `unenforced.test.ts` against upstream's `ENFORCED_KEYWORDS` rather than a hard-coded array.

**M3 · The documented way to reach `<tosi-crud>`'s composed parts throws, and the snippet is in a display-only fence so no lane runs it** — `src/crud.ts:105`, `:455` _(merged: docs + dx)_
`tosiCrud({store}).table` throws `elementRef "table" does not exist!`. `get table()`/`get form()` are the only two accessors on the class with no `this.hydrated` guard (`value`, `search`, `store`, `applySelection`, `render` all have one). The fence is ` ```typescript `, which `insert-examples.ts:68` does not execute. Worse than reported: the snippet's **second** line is wrong even when it doesn't throw — `render()` sets `this.parts.form.readOnly = !canSave` unconditionally (`crud.ts:825`) on every queued render, so a documented `crud.form.readOnly = true` is silently reverted on the next frame. Both lines of a two-line example contradict the claim above them.

**M4 · `<tosi-schema-form>` is quadratic in the keystroke path** — `src/schema-form.ts:1433`
Measured on the _real_ built component in Chromium (worse than the reviewer's synthetic numbers): 200 fields → 9.8 ms/keystroke; 400 → 40 ms; 800 → 240 ms; `value=` round-trip 468 ms. Four consecutive doublings each quadruple the time. At 3200 fields validation is 0.19 ms against 315 ms of `querySelector` (1600:1) — the cost is the lookup, not validation. `handleFieldInput` runs `refreshErrors()` → `syncErrors()` synchronously on every keystroke with no debounce, and both `syncErrors`/`syncValues` do one unindexed attribute-selector scan per field over an O(fields) subtree. Fix: build a `Map<path, {control, wrapper, errorSlot}>` while the DOM is constructed, invalidate at `afterStructuralEdit()`/`rebuild()`. _(The `expanded()`-called-three-times sub-claim did not reproduce at the stated magnitude — ~3 ms/pass at 800 elements, ~2% of the cost. Real, but a minor contributor; hoist it while you're there.)_

**M5 · Adding or moving one array item rebuilds the whole array and drops focus off the control just clicked** — `src/schema-form.ts:1036`
Measured: 5 items → clicking ↓ leaves `document.activeElement === document.body` and **0 of 5** row elements survive (siblings are destroyed too, not just the edited row). 200 items = 4,202 elements, 31.7 ms/click; 800 items = 16,802 elements, **329.6 ms**. You cannot press Enter twice to move an item two positions, and you cannot keyboard-add two rows in a row. The component's own comments assert the opposite in three places ("Only the edited array is rebuilt"; "the array's own items genuinely did change, so rebuilding those is honest") — true one level too coarse. Fix: reconcile rows (`insertBefore` for add/move, remove one for delete); at minimum capture and restore focus by role+index. **Note for the coverage lane:** the unit lane cannot observe this path at all — `CSS` is `undefined` in happy-dom, so `CSS.escape(node.path)` inside `afterArrayEdit` throws a swallowed ReferenceError and `fillArray` never runs.

**M6 · `<tosi-crud>` writes `history.replaceState` on every search keystroke** — `src/crud.ts:614`
`this._hash?.set('q', …)` is the _first_ statement, before the debounce is scheduled. 6 synthetic inputs → 6 `replaceState` calls (verified). WebKit throws `SecurityError` past **100 calls / 10 s** (measured — the finding said 30 s; corrected). At that rate ordinary 40 wpm typing does _not_ trip it, but held-key auto-repeat (~15–30 events/s clearing a long term) reaches it in 4–7 s, as does sharing the counter with crud's own `select()` pushes or a hash router. When it throws, the throw precedes `setTimeout`, so **zero** `store.list` calls fire — search silently stops working plus an uncaught error, and `get search()` reads from the hash so crud's own notion of the term goes stale too. Fix: keep the in-memory update immediate, coalesce the `replaceState` onto the existing `searchDelay` timer; wrap `history.*` in `hash-state.ts` defensively. The same undebounced pattern is what `hash-state.ts:19` recommends to consumers.

**M7 · `resolvePreviewHost`'s `??` chain treats an empty `PREVIEW_HOST` as set, swallowing the site config _and_ the new `~/local-secrets` rung** — `bin/resolve-site-config.ts:216`
Reproduced end-to-end: `PREVIEW_HOST='' bun run bin/caddy-install.ts` prints "No preview host." exit 1 — and its remediation text tells you to create `~/local-secrets/tosijs-preview.env`, a file that exists on this box with a working value. `??` only skips null/undefined; `env: PREVIEW_HOST: ${{ secrets.X }}` renders `''` when the secret is absent. This is precisely the symptom the new rung was added to abolish (`resolve-site-config.ts:157-161`). Affects all three published bins, and `PREVIEW_SSH=''` / bare `--host=` too. `bin/tunnel.ts:114` already uses truthiness for `hostSource`, so the same file contradicts itself. Fix: `[...rungs].map(v => v?.trim()).find(Boolean)`. Add tests for `PREVIEW_HOST=''` with a config host, and one that actually reaches the `~/local-secrets` rung (every existing test supplies a `configHost`, so the new rung is never exercised). _(Correction to the write-up: the `??` chain is pre-existing, carried over verbatim from three copies at v1.10.2 — what's new is that it now also swallows the new rung.)_

**M8 · The redemption gate is exhaustively unit-tested; nothing tests that the dev server goes through it** — `src/doc-system/site/dev-server.ts:1483`
`createRedemptionGate` has 21 tests. The wiring that makes any of it real — `await redeemGate(...)`, the `RedemptionBusyError` → 503 branch, and `const arrivedAt = Date.now()` captured on **arrival** rather than inside the closure — is covered by no test in any lane; `handleRequest` is an unexported closure. Reverting to a direct `redeemLink(...)` (literally the pre-diff line) restores both the unbounded queue and the unthrottled guess rate, type-checks cleanly, and leaves 1102 unit + 49 Playwright tests green. This is the one security control on a path reachable unauthenticated over the tunnel, and the file's own established pattern (`mayReadSite`, `shouldInterceptLinkToken`, `isLockedDown`, `resolveLinkArrival` are all extracted and tested) makes the fix cheap. _(Dropping the `await` specifically would be caught by `tsc --noEmit`; the other two regressions would not.)_

**M9 · The release's own gating document still reads "Verdict: BLOCK" with 59/59 boxes unchecked, several demonstrably fixed** — `RELEASE-REVIEW-1.11.md:1`
`grep -c '^- \[x\]'` → 0 against 59 `- [ ]`. All three headline evidence claims are stale: `release-check` now exits 0 ("95 annotations, all accounted for"), `package.json` reads 1.11.0 (not 1.10.2), and `peerDependencies` declares `tosijs-schema ^1.8.0` (not absent) — so B3 is fully resolved and still filed under "BLOCKERS (3)". Individual items are genuinely mixed: `tunnel.ts` wording, `data-table.ts:2885` fragment concatenation and the `UPSTREAM.md` tjs-lang refresh all landed; `site-config.ts:477`, `TODO.md:760`, the `utilities.md` stub, the `crud.table` throw and the `schema-form.md` dead link are all still live. The cost is evidenced in-repo, not hypothetical: #50 and #77 were claimed fixed in the 1.10.2 notes using this same untracked format and are still open. **Sweep this file before `git tag`** — a checklist where done and not-done look identical is not a gate.
