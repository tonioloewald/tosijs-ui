## Fix before the tag (verified majors; no re-review needed)

- [ ] **Security: a proposal whose `reason` or `source` is an object injects HTML.** `buildProposal` in `/Users/tonioloewald/tosijs-ui/src/schema-form.ts` (about lines 2525 and 2539) passes both straight to `span(...)`; tosijs treats a plain object as props and sets `innerHTML`. Reproduced in happy-dom: `reason: {"innerHTML":"<img src=x onerror=alert(1)>"}` renders the `<img>`. Proposals are agent- or remote-authored JSON by design. Fix: render only when `typeof === 'string'`, or coerce with `String()`. The same coercion is worth applying to `label(node.label)`, `summary(node.label)` and `entry.help` (unverified, developer-supplied input).
  - Clears it: a unit test through `tosiSchemaForm()` asserting that object-valued and markup-string `reason`/`source` produce zero child elements; it must fail with the coercion reverted.
- [ ] **Correctness: accepting an array-valued proposal writes the value but leaves the old rows.** `acceptProposal` (lines 1732-1740) calls `syncVariants()` and `afterStructuralEdit()`; nothing calls `fillArray`. Reproduced: value `['a','b','c']`, one row shown, `change` fired. The same gap exists for `form.value = ...` with a different array length, which predates this diff. Fix: re-fill arrays at or under the accepted path; a general `syncArrays()` from `render()` closes both.
  - Clears it: a test that accepts `{tags:{value:['a','b','c']}}` and counts three `.schema-item` rows, plus one for the `value` setter if the general fix is taken.
- [ ] **Correctness and docs: a proposal on an array, object or union that is on screen is listed as "Proposed changes to fields not shown here" with no Accept/Reject.** `syncProposals` (2459-2496) places proposals only where `_index` has the path, and `_index` holds leaf and plugin fields only. Reported by both the correctness and docs lenses; merged here. Either render the proposal on the container, or state the leaf-only limit in the Proposals docs and reword the orphan line so it does not claim a visible field is hidden. Rendering on the container is the better fix, because "replace the whole thresholds list" is snowfox's stated shape. If Accept is offered on containers, the stale-rows fix above must land with it.
  - Clears it: a Playwright case with proposals on `tags`, `box` and `limits.0.value` asserting whichever behaviour is chosen.

## Follow-ups to file: this repo (virta board; `TODO.md` is a pointer)

Verified minors and nits:
- [ ] **Accept and Reject drop keyboard focus to `<body>`** (correctness, confirmed by code reading). `syncProposals` removes the element holding the focused button and nothing restores focus; `afterArrayEdit` in the same file already treats this as a defect. Move focus to the field's control or the next proposal, and assert `toBeFocused`. This is cheap enough to fix with the majors.
- [ ] **Form-level `readOnly` does not stop a custom `proposalView` from accepting** (security and docs, confirmed by code reading; merges three findings). Only `.schema-proposal-actions` is hidden; `ProposalContext` has no read-only flag and the `accept` callback stays live. The doc sentence "shows the proposals with no buttons" is untrue for a custom view. Add `readOnly` to `ProposalContext`, or make the context callbacks no-ops, and qualify the doc. Programmatic `acceptProposal()` on a read-only form is consistent with the documented "proposals are presentation" stance and is not counted as a defect.
- [ ] **`FieldCuration` widened to include `CuratedSection`** (blast-radius, confirmed). Adopter code that reads `entry.caption` after `typeof entry === 'object'` now fails with TS2339 on a patch. The claimed TS2345 on `curatedField(entry)` did not reproduce; a section passes the type check and is silently treated as a field. Add a CHANGELOG note pointing at `isSection`, and export or document it.
- [ ] **Array-item layout fix overrides an adopter's own `.schema-item` grid** (blast-radius, plausible, downgraded to nit). Add a CHANGELOG clause that item children are now explicitly placed; ask snowfox whether they carry a local CSS workaround.
