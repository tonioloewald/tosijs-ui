## Majors — fix before the tag, or dispositioned explicitly (all verified)

### F1 — The #128 write allow-list still admits executable build scripts the build spawns every rebuild
**`src/doc-system/site/editable-sources.ts:25`** · lens: security · verified · severity flagged uncertain by the lens, kept at major

Against the **real shipped corpus** (not a synthetic one): `editableSourcePaths(demo/docs.json, repoRoot)` yields 66 paths, and `mayEditSource(<root>/bin/make-icon-data.js)` → **true**; `bin/release-notes.ts` → true. `bin/dev.ts:80` runs `await $\`bun ./bin/make-icon-data.js\`` in `prebuild` — every build and every watch rebuild. So a tunnel invitee holding a redeemed link session can POST `{file:'bin/make-icon-data.js', content:'<arbitrary JS>'}` to `/__docstore/source`, get 200, and have it execute with the developer's privileges at the next rebuild. That is verbatim the class `dev-server.ts:970` says the change closes (`bin/` is named there as one of the surfaces that "executes on the next ordinary command").

The unit test asserts `bin/dev.ts` is refused — but only because the 3-entry synthetic corpus omits `bin/` files. A corpus that documents its own tooling (which this project does, and recommends) puts them back. The hostile case — *a corpus entry that is itself an executed file* — is untested; the commit body's live verification used `.git/hooks/pre-commit`, which the corpus never contained.

Generalises to adopters: any project with `/*#` blocks in a build script hands write access to that script.

**Fix:** intersect the corpus-derived set with the doc source roots the endpoint needs (refuse anything outside `src/` + `docs/` + top-level markdown, or explicitly subtract `bin/` and anything the build spawns), and add a test whose corpus **contains** `bin/make-icon-data.js` and asserts refusal. If the residual is accepted instead, say so where the guarantee is stated — do not leave code claiming `bin/` is excluded.
*Re-review scope if fixed: correctness + security over the remediation diff only (the predicate and its tests).*

### F2 — Only the WRITE half of `/__docstore/source` was narrowed; the READ half serves any file under the repo root, and the new docstring claims otherwise
**`src/doc-system/site/dev-server.ts:936`** · lenses: security + blast-radius (deduped) · verified

`handleWriteSource` gates on `mayEditSource(resolved, await allowedSources())` (line 974). `handleReadSource` (936) resolves through `resolveInRepo` and nothing else, then returns `Bun.file(resolved).text()`. The route at 2143–2155 computes **one** `authorized` value and dispatches GET→read, POST→write — so anyone who can write can read, unconstrained beyond root containment.

Reachability holds: `csrfOk = viaTunnel || isSameOriginRequest(request)` and `mayWriteSource` returns `hasValidSession` when `viaTunnel`. `tls/key.pem` (1708 bytes, gitignored via `.gitignore:90 *.pem`) is present and readable this way, as are `.env` and `.git/config`. The magic link is documented in `dev-auth.ts` as a 5-minute bearer token that "LEAKS: browser history, Referer headers, reverse-proxy access logs, link previews in chat apps", redeemable for a 30-day session cookie. The invited capability is "look at and edit my docs on a headset"; the actual capability is "read my whole working tree".

The read breadth **pre-dates** this release (and `doc-site-system.md:333` does note it) — but the misleading docstring is new: `editable-sources.ts:2` says "WHICH files `editableSources` may touch" and `:25` says "Absolute paths the source editor may **read or write**", while no read-path caller references either export. The comment block above `resolveInRepo` (921–923) is also now stale ("Local dev only — your machine, your files… No auth/token"). Issue #128 is **closed** with the deferral recorded only in its closing comment; `grep 128 TODO.md` finds nothing, so nothing tracks it.

**Fix:** one line — `if (!mayEditSource(resolved, await allowedSources())) return 403` in `handleReadSource`. The editor only ever reads the source of a page in the corpus, which is exactly that set, so it is behaviour-neutral. If the deferral stands for this release, correct the docstrings to "may write" and note the read exposure in `doc-site-system.md`'s tunnel/invite section, and re-open a tracking item.

### F3 — `audit.blockOn` is a shipped, typed, documented option read nowhere; `audit-reach.ts` is imported by nothing
**`src/doc-system/site/audit-guard.ts:208`** · lens: correctness · verified

Repo-wide grep finds `blockOn` at exactly two sites: its declaration and one prose reference in `audit-reach.ts:23`. `auditDependencies` destructures only `cfg.level` and `cfg.allow`; the blocking decision is severity rank + gate matching, with no reach input. `audit-guard.ts` never imports `audit-reach.js`, and `audit-reach` is not re-exported from `src/doc-system/site/index.ts`. It **ships**: `dist/doc-system/site/audit-guard.d.ts:71` carries `blockOn?: 'severity' | 'runtime'` with the JSDoc.

The JSDoc's claim that "Build-only findings are LABELLED either way" is **false without qualification** — there is no reach field on `AuditAdvisory`/`AuditResult` and `reportAudit` prints no reach label. The consumer this was built for (the monorepo with 18 high/critical advisories, few runtime-reachable) sets `blockOn: 'runtime'`, type-checks clean, still fails on every build-only advisory with no label — and the next thing they reach for is `audit: false`, the exact outcome the option exists to prevent.

Fail direction is safe (the gate stays stricter than requested), and the other half of the same commit — the PASSING-ON-A-WAIVER marker — **is** wired and tested. TODO.md:94 still lists #56 as unchecked.

**Fix:** either wire `classifyReach` into `auditDependencies`/`reportAudit` and honour `blockOn`, or remove `blockOn` from the exported `AuditConfig` and the labelling sentence, leaving `audit-reach.ts` as tested groundwork.

### F5 — #93: the machine-health guard now *sees* orphaned `--watch` bundlers but still cannot flag them; the changelog reads as coverage
**`src/doc-system/site/preflight.ts:119`** · lens: correctness · verified · severity flagged uncertain

Dropping the `--watch` exemption makes those processes candidates, but every trigger in `assessProcesses` is per-process RSS (`catastrophicPct` 50%, `hugeDevPct` 25%, `devLimitMb` 4096MB). Reproduced: 69 orphans × 194MB (the reporter's actual table, 13.09GB total, 5h old) → `{ level: 'ok', offenders: [], reason: '' }` at both 128GB and 32GB `totalRamMb`. The new tests are six `isDevProcess` unit assertions; nothing drives `assessProcesses` with a fleet of small orphans, so the suite is green and the reported machine still assesses `ok`.

Fair to the change: it does close a real gap (a `--watch` bundler past 4GB or 25% of budget is now visible where it was permanently exempt), and the reaping idiom added to `doc-site-system.md:492-519` addresses the leak at source.

**Fix (cheapest honest option):** one sentence in the CHANGELOG entry, the `isDevProcess` comment and `assessProcesses`' doc comment saying candidacy is not a trigger and that reaping, not the guard, is the fix for many small orphans.
