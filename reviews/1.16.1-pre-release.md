## Blockers (must clear before `git tag`)

### B1. Uppercase-language fences lose their content and break save-to-source ordinals (correctness, major, **confirmed**)
`src/live-example/insert-examples.ts:152`
- **What changed:** the selector widened from the six case-sensitive `.language-*` classes to `[class*="language-"]`. The capture `/(?:^|\s)language-(\S+)/` keeps the author's case, and `isLiveFence` lowercases it. Together they make ```` ```HTML ```` / ```` ```JS ```` fences live, and in v1.16.0 they were static.
- **What happens (reproduced in happy-dom):**
  - `HTML` falls through `switch (source.language)` to `default` and hits `break`. `source.block.remove()` then deletes it, so the author's HTML disappears from the page.
  - `JS` runs with `dialect='JS'`, which fails the `!== 'js'` comparisons and takes the non-js path.
  - insert-examples produced 3 ordinals where `groupExamples` found 2, because `parseFenceInfo`'s `^[a-z]+` rejects uppercase. That means an edit gets saved over the wrong block. This is the exact failure described in the `example-policy.ts` docblock.
- **DRY cause:** this line is a second copy of the `language-*` class grammar. `highlight.ts` `LANGUAGE_CLASS` says it is the only place that grammar is written, and that copy lowercases and uses a different character set.
- **Fix:**
  - Export `highlight.ts`'s `langOfClass` and use it here instead of the new regex.
  - Make case handling agree between `isLiveFence` and `parseFenceInfo`. The simplest option restores 1.16.0 behaviour, where an uppercase fence is static.
  - Never `remove()` a block the switch did not consume.
  - Add a unit test with an uppercase fence asserting that insert-examples and groupExamples produce matching ordinals.

### B2. A replaced built-in `tjs` dialect only takes effect in dev (correctness, major, **confirmed**)
`src/live-example/component.ts:1897`
- **Why it happens:**
  - `check-examples.ts` bakes every tjs fence with the pinned transpiler, hardcoding `dialect: 'tjs'`, and never sees page registrations.
  - The runtime `bake` condition does not check `isBuiltInDialect`.
  - So with tests off (deployed readers), `registerDialect('tjs', { transform })` is ignored and readers get the pinned output. In dev they get the override.
- **Result:** the same example runs different JS in dev and in production, and this is a documented feature of this release (`component.ts:129`, `dialects.ts:62`).
- **Fix:**
  - Add `isBuiltInDialect(this.dialect)` to the bake condition, mirroring `dialectTransform`.
  - Add a unit test: register a `tjs` override, set `compiledJs`/`compiledJsSource` with tests disabled, and assert that the override ran.

## Follow-ups (non-blocking; file them, don't drop them)

### Destination: this repo's task board (virta; `TODO.md` is now a pointer)

- [ ] **Menus: iOS rubber-band / off-screen dismissal. This is the maintainer's report.** (blast-radius, minor, **confirmed**) `src/search-field.ts:716`, `src/float.ts:204-222`, `src/menu.ts:1612`, `src/pop-float.ts:331,396`.
  - **Why it happens:**
    - search-field fixed "a scroll dismisses the popup" with its own private document-scroll listener. Float, menu and pop-float are byte-identical to 1.16.0.
    - `popMenu` still uses `remainOnScroll: 'remove'`, and float's global capture listener removes the float on *any* document scroll.
    - On iPhone, a menu whose top item is off-screen is dismissed the moment the user scrolls or rubber-bands the page to reach it.
    - `positionFloat` measures with `window.innerHeight` and sets `--max-height: calc(100vh - …)`. On Mobile Safari `100vh` is the large viewport, so a menu can extend past what is visible.
  - **Fix plan:**
    - **(a)** Make `positionFloat`/`--max-height` use `window.visualViewport`, so a tall menu is capped to the visible area and scrolls internally. The user then never needs to scroll the page to reach the top item. This is the real fix for the reported case.
    - **(b)** Move the scroll-dismiss predicate into TosiFloat (e.g. `remainOnScroll: 'remove-if-anchor-moves'`) and use it from both search-field and popMenu, then delete search-field's private listener. That removes the two-policy twin.
    - **(c)** Add `overscrollBehavior: 'contain'` to the menu sheet and to `.tosi-search-hints` (see next item).
    - Note: copying search-field's predicate as it stands would *not* fix iOS, because it still closes when `target === document`.
  - **Verification:** verify on a real iOS device or simulator. happy-dom cannot reproduce scroll chaining.
- [ ] **search-field hint list has no overscroll containment.** (correctness, minor, **plausible**; actual line is `src/search-field.ts:355`, not :55) When a scroll chains out of the end of the hint list to the document, the list closes mid-gesture. This happens on iOS, and on desktop wheel whenever the page itself can scroll. Add `overscrollBehavior: 'contain'`, a pattern already used in `data-table.ts:1345`. Optionally ignore document scrolls while a touch that began inside the list is active. Fold into the menu task above.
- [ ] **search-field: stale `this.float` after `popFloat` removes the float on resize** (correctness, minor, *unverified*) `src/search-field.ts:387`.

  - **Fix:** treat "open" as `this.float?.isConnected`, or pass `'remain'` and close the hints yourself.
  - **Related (completeness gap):** the Android keyboard resizes the viewport, so the list may close as soon as it opens.
