## Blockers

### B1 — `import 'tosijs-ui/doc-browser'` never defines `<tosi-doc-system>`; the no-op ships in four places including a `.d.ts` (#158, #159)
**Lens: ecosystem · verified (confirmed) · `src/docs/adopting-the-doc-system.md:41`**

Reproduced at HEAD, not assumed:

- `dist/doc-browser.js` contains **zero** `elementCreator()` calls (`grep -c` → 0; the one textual hit is inside a preserved `/*#` comment), and its 39-module transitive relative-import graph never reaches `dist/doc-system/doc-system.js` — the only module with `preferredTagName = 'tosi-doc-system'` and its `elementCreator()`. The arrow runs the other way (`src/doc-system/doc-system.ts:74` imports from `../doc-browser.js`).
- Runtime probe (happy-dom, importing the built files as a bundler would): after `dist/doc-browser.js` → `tosi-doc-system=false`, `tosi-sidenav=true`, `tosi-example=true`, `window.__docTestResults=undefined`. Adding `dist/doc-system/doc-system.js` → `tosi-doc-system=true`.
- An adopter following our adoption page verbatim therefore gets leaf components plus an **inert `<tosi-doc-system>`**: no header, no nav, no menu, and — the costly half — **no `__docTestResults`, so their doc-test corpus silently stops existing.** `createDocBrowser` ships but is never invoked (its only production caller is `doc-system.ts:615`).
- The working spelling `tosijs-ui/doc-system/doc-system` resolves only through the undocumented `./*` wildcard and appears in **no** doc page (grep over `src/docs/`, `doc-site-system.md`, `README.md` → nothing).

Four shipped texts carry the wrong instruction, unchanged in the 1.15.0 diff:
- `src/docs/adopting-the-doc-system.md:41` (and `:94`)
- `src/doc-system/site/orchestrator.ts:1222` — the text the build prints **when it detects the problem**, so the remediation advice is itself the no-op
- `src/doc-system/site/site-config.ts:117` — **ships in `.d.ts`**; `:130` additionally still claims `import 'tosijs-ui'` "also works and registers everything", false since #133 removed the cluster from the barrel in 1.14.0, and enforced false by `src/index.test.ts:19`
- `src/doc-system/doc-site-system.md:148` — same false root-barrel claim in the published adopter reference

Two adopters hit this independently against 1.14.x: **#158** (tosijs-3d-ensemble, with a measured marker table) and **#159** (tosijs-product, an inert site reached a release candidate). Neither issue is mentioned in `TODO.md` or the CHANGELOG. 1.15.0 republishes all four texts unchanged while adding a fifth subpath (`./highlight-block`) to the same model.

**Fix before tagging:** give the registrar a named export (`"./doc-system": dist/doc-system/doc-system.js`) or have `doc-browser` import it for side effect; then sweep all four texts together (including deleting the false root-barrel sentences in `site-config.ts:130` and `doc-site-system.md:148`). Add a `bin/smoke-consumer.ts` assertion that the documented import line produces a `customElements.define('tosi-doc-system'` in a built bundle. Close #158/#159 naming the version, and say so in the release notes — an adopter on 1.14.x is shipping a site with no doc-test corpus.
**Re-review scope:** correctness + blast radius over the remediation diff, plus one `bun run test-consumer` run (the claim is about resolution from a foreign cwd; nothing in-repo can check it).

## Majors (non-blocking; file as follow-ups)

### M1 — `bundleRegistrations` reports a false green on an inert build (#159)
**Lens: ecosystem · verified (confirmed) · `src/doc-system/site/host-preset.ts:126`**

The guard is `bundleSource.includes('tosi-doc-system')`. A substring is not a registration. Reproduced with a real `bun build --minify` of a realistic adopter entry (one unrelated `customElements.define` plus the context-map loop `document.querySelectorAll('tosi-doc-system')` our own API invites): `{ docSystem: true, liveExample: false }` with exactly **1** `define` in the bundle, none of it the doc system — byte-for-byte the row #159 tabulated. `orchestrator.ts:1215-1233` then falls through to warn about a **different** component, pointing the maintainer away from the defect.

Aggravating: the triggering shape is our own documented recommended entry (`doc-site-system.md:148-153`), so copying our docs verbatim yields an inert site **and** a green guard. This is the safety net for B1, so both layers of the release's headline theme are currently down. The shipped `host-preset.d.ts:43-45` asserts "this is the one case where grepping a bundle is sound" — a necessary condition read as sufficient, the same class `CLAUDE.md` already records — and `host-preset.test.ts:142-145` enshrines the claim, which is why the false positive survived.

### M2 — tjs-lang pinned to 0.13.11 while 0.13.12 has been `latest` since 2026-09-07, carrying the fix for open issue #135
**Lens: ecosystem · verified (confirmed) · `src/live-example/code-transform.ts:300`**

`TJS_VERSION = '0.13.11'` and `devDependencies.tjs-lang: 0.13.11`. Reproduced the upstream defect rather than trusting the changelog — running the same source through both `dist/tjs-browser.js` bundles:

- Source `const doc = "test 'sneaky' { globalThis.__LEAKED = true }"`.
- **0.13.11** → emits `const doc = ""` (string silently emptied) **and** `globalThis.__LEAKED === true` at transpile time, in the transpiling context, outside the iframe sandbox `execution.ts` provides.
- **0.13.12** → string preserved, `__LEAKED === false`. Template-literal form behaves identically.

Two records that should have caught this are stale in the same direction: `TODO.md:1043` says "**0.13.12 is not published yet**", and `UPSTREAM.md:410` reads "_Status checked 2026-08-24._ Latest published tjs-lang is **0.13.2**" — 21 days old against that file's own mandated weekly re-poll.

Scope corrections, which do not change severity: the 0.13.11 bytes reach only the CDN/IIFE path and **tosijs-ui's own published doc site** (an adopter with tjs-lang installed resolves their own, under peer `^0.13.1`) — one way, not either way; 0.13.12's security half (#52/#54) is unreachable here (nothing imports `tjs-lang/eval` or `/vm`); and the current corpus has zero quoted test blocks, so the exposure is latent. It still matters because 1.15.0 is the release that makes tjs authoring first-class (`registerGrammar`, `:static`, the `tjs` alias) — exactly what invites such a corpus. **Note for whoever bumps:** 0.13.12's output is not byte-identical (runtime prelude restructured into an IIFE), so run the lanes rather than treating it as a no-op.

### M3 — prismjs takes ownership of `window.Prism` with no seam, no UPSTREAM record, and no consumer-facing note
**Lens: ecosystem · verified (confirmed) · `src/doc-system/highlight.ts:201`**

Executed, not read. Seeding a host Prism with a custom language and plugins, then calling `ensureGrammar('rust')`:

```
ensureGrammar(rust) = true
globalThis.Prism is host? false      window.Prism is host? false
host custom lang reachable? false    host plugins reachable? false
host object intact itself? true      global has rust? true
```

Our instance takes the global, the host's languages/plugins become unreachable through `window.Prism`, their captured reference points at an orphan, nothing errors. Two sharper mechanisms the finding did not name: Prism's grammar component files register against a **free global** (`…})(Prism)` survives minification into `dist/iife.js`), so a host Prism loading between our core and a grammar import silently steals our registrations (`ensureGrammar` then returns false, no highlighting, no message); and our pre-write leaks `manual: true` onto the global, so a host Prism core loading **after** us computes `manual === true` and silently never runs `highlightAll()` — us breaking a host page, not merely losing the global.

This is the #131 hazard class (`@codemirror/state`) with a worse container. That case got a real remedy (`tosijs-ui/codemirror` re-export); prism got none — there is no `./prism` key in `exports`, and `registerGrammar` supplies grammars, not instance access. `grep -i prism UPSTREAM.md` → **0 matches**, in a 785-line file with sections for bun, tosijs, tjs-lang, haltija and tosijs-schema. Blast radius is bounded: in `dist/iife.js` prism core and its 28 grammar sources sit inside bun's lazy `__commonJS` wrapper, so the clobber fires on the first `<tosi-highlight>`/`highlightBlocks` call, not on load — immediate on a doc page. Carried over unaddressed from the 1.15.0 re-review, where it was logged as a minor.
