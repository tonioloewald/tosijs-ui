## Fix before the tag

- [ ] **Non-string union branch titles still reach `option()` as element properties** (major, verified by both lenses; deduped).
  - **Where:** `/Users/tonioloewald/tosijs-ui/src/schema-form/fields.ts:216` (`(b as any).title || String(b.const)`) and `:256-258` (variant branches) still pass a non-string title through. Only the property-title rule at `:327-330` was fixed.
  - **Sinks:** `/Users/tonioloewald/tosijs-ui/src/schema-form.ts:2122` (`option({ value: String(i) }, branch.label)`) and `:2488` (`option({ value: String(o.value) }, o.label)`) are the two label sites without the `String()` wrap.
  - **Effect:** reproduced under happy-dom; the correctness lens also measured it in chromium. A `oneOf` const with `title: { innerHTML: '<img class="injected">', value: 'HIJACK' }` renders `<option value="HIJACK"><img class="injected" src="x"></option>`, so markup is injected and the submitted value is overwritten.
  - **Bound:** a JSON-sourced schema cannot carry functions, so this is markup/class/value injection, not handler injection. The two sinks predate this diff.
  - **Why before the tag:** `CHANGELOG.md:36-37` says "Only a string is a title now; anything else falls back to the key", which is false for these paths.
  - **Fix:** one `titleOf(schema): string | undefined` helper used at all three sites in `fields.ts`, plus `String()` at the two option sinks.
  - **Check that clears it:** extend the "only a string is a title" unit test in `src/schema-form/fields.test.ts` with a variants `anyOf` and a consts `oneOf` whose titles are objects. Assert `branches[i].label` / option labels are strings, and that the rendered form has no injected child element and an unchanged `option.value`. The test must fail with the fix reverted.

Unverified (leads only; sanity-check before acting):

- [ ] (unverified, minor, correctness) Accepting a non-array proposal for an array path throws `forEach is not a function` in `fillArray` (`src/schema-form.ts:2035`). This happens after `proposalaccept` has fired and the proposal is gone, with no `change` event. Suggested fix: `Array.isArray(list) ? list : []`, as `syncArrays` already does.
- [ ] (unverified, minor, correctness) A proposal for a whole array item that is an object (`thresholds.0`) is reported as "not shown here" and has no Accept button (`src/schema-form.ts:2045`). Register the row as a host for `${node.path}.${index}`, or document that an array item as a whole is not a proposal target.
- [ ] (unverified, minor, correctness) Accepting a whole-array, object or union proposal leaves item-level proposals attached to whatever now sits at that index (`src/schema-form.ts:1801`). Drop proposals under the accepted path in `acceptProposal`, or document that they stay by path.
- [ ] (unverified, minor, correctness) `focusAfterProposal` drops focus to `body` when the next undecided proposal is inside a closed `<details>` or under a hidden actions span (`src/schema-form.ts:1780`). Pick the first candidate that can actually take focus, falling back to the wrapper or summary. No test covers this.
- [ ] (unverified, minor, blast-radius) The guard against tosijs reading an object child as props is applied call-site by call-site (`src/schema-form.ts:2459` and about ten others), which is how the two option sinks were missed. Enforce string-ness in the producers (`fieldsFor` / `unionOf` / `curate`), or add one test that walks a schema whose every title, caption, help and section is an object and asserts no element gained a child element. Record the tosijs#43 workaround beside the code. The same shape exists at `span(item.caption)` in `src/menu.ts:1158-1404`.
- [ ] (unverified, minor, blast-radius) A proposal dropped or re-keyed by `removeArrayItem` → `rekeyProposals` (`src/schema-form.ts:2302`) fires no event. Apps tracking outstanding proposals from `proposalaccept` / `proposalreject` hold stale paths. Fire an event, or document that apps must re-read `form.proposals` after any `change`.
- [ ] (unverified, nit, correctness) Curated help on an array moves from after Add to after the summary on the first re-fill (`src/schema-form.ts:2040`). Insert help directly after the summary in `buildNode` so both orders agree.
