## Fix before the tag

- [ ] **(major, verified, correctness) An inline-view tjs example reports an inline-test failure, but the "tjs tests" tab is never created and clicking the status line does nothing.** `src/live-example/component.ts` (`ensureProductTabs`, about line 2005; `showTestsTab`, about line 2188).
  - **Cause:** with tests off (the deployed default), the IntersectionObserver calls `showInline` → `ensureProductTabs` while `refresh()` is still awaiting the transpiler. `inlineTjsTestCount` is 0 at that point and `productTabsReady` latches. `renderTjsTests` later updates the status line and returns without creating the view.
  - **Why it matters:** this is the #219 case, and the docs and CHANGELOG both say "clicking it opens the tab with the detail". The failure text itself is still visible in the line and its tooltip.
  - **Fix:** create the tab when results arrive: in `renderTjsTests`, if `productTabsReady && inlineTjsTestCount > 0 && !tjsTestsView`, append the view and call `setupTabs`.
  - **Clears with:** a Playwright case in `tests/example-views.pw.ts`: tests off, a tjs example with one failing inline test in `view: code`. Assert the `tjs tests` tab exists and a click on the status line selects it. It must fail with the fix reverted.

Reconcile the wording, then re-run as the last step before `git tag`; tagging would turn the gate green without the fix.

## Follow-ups: this repo's board (`TODO.md` is the pointer)

### Minor

- [ ] **(verified, correctness / blast-radius / security, three findings merged) `deadInPageAnchors` misreads raw HTML, and it can fail a `strict` build.** `src/doc-system/site/build-warnings.ts:77`.
  - **False positives (reproduced):** a second id-like attribute on one tag (`<input name="foo" id="bar">`), single-quoted or unquoted ids, and a `>` inside an earlier attribute value. Each throws `SiteMisconfiguredError` under `strict: true` on a link that works, and there is no per-anchor opt-out.
  - **False negatives:** single-quoted or unquoted `href` values are never checked, and any element's `name=` counts as a target.
  - **Reach:** hand-written HTML in markdown only; markdown-authored links and headings are unaffected.
  - **Fix:** match attributes globally in all three quote styles, or parse the HTML; restrict `name` to `<a>`. Add tests for those inputs. Consider a config allow-list for anchors the build cannot see, or state the limits in the function's doc comment and in `doc-site-system.md`.
  - This is the same shape as the 1.16.7 finding: a regex of its own deciding a `strict` build.
- [ ] **(verified but narrowed, efficiency / blast-radius, two findings merged) Every `tjs` inline-view example skips the bake, whether or not it has tests.** `src/live-example/component.ts:3192`. `teaches` checks neither `this.test` nor the inline-test count.
  - **What I checked:** `check-examples.ts:218-226` bakes `tjs` only; `ts` was never baked. So nothing changes for `ts`, and the "new esm.sh dependency" part of both findings does not hold.
  - **What is real:** a `tjs` example with no tests now waits on the same-origin transpiler load and a main-thread transpile before first render, then shows no status line. There is also no fallback to the in-memory bake if the load fails.
  - **Fix:** take the full path only when `this.test` is set or the build-recorded inline-test count is above zero; fall back to the bake on a load failure.
- [ ] **(docs, from the refuted finding) The CHANGELOG overstates the `ts` change.** It says a "`tjs` or `ts` example ... used to run from the build's pre-transpiled copy". `ts` never had one. Two reviewers believed the `ts` path was newly exposed, so the fact that only `tjs` is baked is hard to discover. Correct the CHANGELOG sentence and the matching line in the live-example docs, and say "bakes are `tjs` only" where bakes are documented.
- [ ] **(unverified, correctness / blast-radius, two findings merged) The print book repeats heading ids across chapters.** `src/doc-system/book-html.ts:200`. `buildBookHtml` concatenates every chapter into one document, and `HeadingIds` resets per render. Measured on this corpus: 15 duplicate ids across 70 chapters, none currently pre-empting a chapter's TOC target. An in-page `#usage` link in a later chapter would resolve to the first chapter with that heading. Fix: namespace heading ids and same-page hrefs per chapter; add a two-chapter test.
- [ ] **(unverified, correctness) An inset's `#anchor` cannot name a repeated heading by its page id.** `src/doc-system/site/single-source.ts:141`. `#usage-1` is matched against the un-deduplicated slug. It usually fails loudly with "no such heading". Fix: walk the target's headings through `HeadingIds`; add a test with two same-named headings.
- [ ] **(unverified, docs) `ebooks` is documented only in the CHANGELOG.** `src/doc-system/doc-site-system.md:941` still tells direct `generateSite` callers about `bookVolumes` alone. Those callers keep the legacy, possibly-404 link. Add one sentence: pass `ebooks` (`listEpubVolumes(...)` mapped to `{title, url}`, or `[]`), and say an unset key keeps the derived link.
