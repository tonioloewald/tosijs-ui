## Majors to resolve before the tag (2, both verified)

These were not rated blocker by any lens. I am treating them as release-gating because each is a fail-open in the gate #2874 set out to close, and each is contradicted by a sentence in the 1.16.8 CHANGELOG. Both were confirmed by reading the code, not by runtime reproduction.

**M1. A page that times out after reporting some results is recorded as a pass** (`src/doc-browser.ts:2403`; correctness + security, merged).

- `timedOut` is set at the 45s deadline but is read only inside `if (!pageTestResults[doc.filename])`, where it picks the message text.
- If one example has already reported, the page keeps `totalFailed: 0`, counts toward `pagesTested`, and `testReportVerdict` returns ok.
- The trigger is narrow: the frame must boot more than about 14.5s after `src` is assigned (or navigate itself away) while a later example hangs. That is the slow-load condition #2874 was about.
- The CHANGELOG says a page that "does not finish within 45 seconds, is now recorded as a failed test". The code does that only when nothing was reported.
- No test covers the branch; `noResultsFailure` is tested for the zero-results shape only.
- Fix: when `timedOut`, always append a failed test to the page's entry and bump `totalFailed`. Extract the post-wait decision into a pure function and unit-test it beside `noResultsFailure`.
- Alternative if deferred: narrow the CHANGELOG sentence to "reported nothing" and file the task.

**M2. The host page's results are overwritten per example, so a failure can be dropped** (`src/doc-browser.ts:811`; correctness, plus the current-page half of the security finding).

- `handleTestComplete` replaces `pageTestResults[filename]` on every `testcomplete`, and `testcomplete` fires once per example. The iframe path accumulates instead.
- On a landing page with example A failing and example B passing, B's event erases A's failure and the run goes green.
- The new settle loop treats "an entry exists" as "the page is done", so a slower later example can also go uncounted.
- The overwrite predates this release, but this release rewrote the block and the CHANGELOG says "The page you are on waits for its own results".
- This repo's lanes cannot see it: `README.md` has no test fences and `tests/doc-tests.pw.ts` starts at `/`. An adopter whose home page has two test examples can.
- The comment "A beat for the last example on the page to report after the first has" describes a delay that runs before the first check, not after the first result.
- Fix: accumulate per example, keyed by element so reruns do not double-count, and decide "done" with the same `unsettledExamples` census the iframe path uses. Add a Playwright case that starts the run on a page with two test examples.
- Alternative if deferred: soften the CHANGELOG line, correct the comment, and file the task.

## Completeness gaps

- **No lane is shown green on this HEAD.** `main` is 4 commits ahead of origin, so CI (tsc, format-check, unit, chromium e2e) has not run on it. There is no evidence for `bun test`, `bun playwright test`, `bun run test-browser` or `bun run test-consumer` either. All four plus `bun run build` are required before the tag. `test-browser` matters most, because its pass/fail logic is what this release rewrote.
- **"Recorded exceeds expected" is unanalysed.** `handleTestComplete` writes an entry for whatever page is current, and `testcomplete` also fires on an execution error. A page outside `docsWithTests` can gain an entry and fail the new equality gate with a misleading "20 of 19". `test-report.test.ts` has no case for it.
- **Adopter migration for `devServer --test` was not checked at the boundary.** A client bundle that omits `pagesWithTests` / `pagesTested` (a custom `bundleEntry` built against an older tosijs-ui) may now fail with "recorded for N of 0". F6 claims the opposite outcome for a field-less report. Read `testReportVerdict` and settle which is true before touching either.
- **Lane budget versus the 45s deadline.** `tests/doc-tests.pw.ts` sets `test.setTimeout(180_000)`. Four stalled pages exhaust it, so the scenario #2874 targets would end as a bare Playwright timeout instead of named per-page failures. The same question applies to the haltija lane's overall wait.
- **`hasTestBlock` versus `insertExamples` parity is unchecked.** Fences nested in lists, blockquotes or HTML, and raw `<pre class="language-test">`, may be counted differently. One direction is now a hard failure; the other is a silently untested page. Whether `examplePolicy()` is already set for an `opt-in` site when `startBackgroundTests` runs was not shown. The 1.16.7 re-review recorded the same class for `liveFenceLanguages` (its item 5).
- **Output-only panel surface is unchecked beyond one chromium spec:**
  - Hard-coded light-palette colours with no dark-mode check, against the repo's `vars` rule.
  - `role="log"` is a live region, so log-only examples may announce on load.
  - The ePub, print and no-JS paths still show an empty box.
  - The baked-tjs path on deployed sites skips the inline-test run, so the panel differs between localhost and production.
  - `outputWatch` and `runSettled` are not torn down in `disconnectedCallback`.
- **Packaging.** `dist/doc-system/site/code-fences.{js,d.ts}` moved to `dist/doc-system/`. The `./*` wildcard export means `tosijs-ui/doc-system/site/code-fences` stops resolving in a patch. It is probably unused externally, but nobody stated that. Either note it in the CHANGELOG or leave a re-export; `test-consumer` should run regardless.
- **#210 item 2 on other tjs-lang versions.** The `ts` change was measured on 0.13.13 only. Nothing shows what an installed peer elsewhere in `^0.13.1`, or the CDN fallback, does without the dialect option. No `ts` example in the corpus exercises it, so the doc-test lane does not cover it (see F3).
