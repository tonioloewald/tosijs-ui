## Major findings (3)

### M1 — `bun book` and the public `buildEpub` export bypass the determinism fix entirely _(verified)_

`src/doc-system/site/epub.ts:787` · `bin/build-book.ts:15` · `src/doc-system/site/orchestrator.ts:379`

_(Deduped: reported independently by the correctness lens at major and the blast-radius lens at minor. The two verifiers split on severity — the blast-radius verifier downgraded on the "no regression on upgrade" argument, which I accept for the blocker question but not for the fix-now question. Recorded at major with that dissent noted.)_

`epubOptionsFor()` lives in `orchestrator.ts`, has exactly one call site (`buildSite`, line 1360), and is **not re-exported from `src/doc-system/site/index.ts`** — adopters cannot reach it. `buildEpub` **is** public (`index.ts:34`) and is what `bun book` calls directly. That path lands on `epub.ts:787`:

```ts
modified: (opts.modified ?? new Date().toISOString()).replace(/\.\d+Z$/, 'Z')
```

No `Date.parse` validation, no deterministic default. Reproduced by driving the real public export:

- `{ modified: '2026-09-03' }` → OPF `<meta property="dcterms:modified">2026-09-03</meta>` — EPUB 3 requires `CCYY-MM-DDThh:mm:ssZ`; EPUBCheck rejects it (RSC-005).
- `{ modified: 'not a date' }` → passes through byte-for-byte.
- `{}`, two runs 2s apart → `…10:50:04Z` / `…10:50:06Z` — a wall clock, so the documented `bun run build && bun book` sequence re-dirties the committed `docs/tosijs-ui.epub`. That is precisely the non-determinism this release headlines as fixed.

The sharp part is the propagation argument: the four new `epubOptionsFor` tests drive a path the public export never executes — **the same "green test asserting a function whose only consumer discards the result" shape the CHANGELOG names three times in this very diff**, reproduced by the fix for it. The CHANGELOG's justification ("the shipped path and the tested path are the same object rather than two things that agree until they don't") is true of one of the two shipped paths.

**Fix:** move the default _and_ the `Date.parse` validation into `buildEpub` — `versionAnchoredDate(version, opts.modified)` — so `buildSite`, `bun book`, and every adopter calling the public export inherit it. Leave `epubOptionsFor` the `bookTarget` assembly only. Add one test that drives `buildEpub` (not the helper) with `{ modified: '2026-09-03' }` and asserts the OPF text.

### M2 — The block comment above `epubOptionsFor` still asserts the monotonicity this commit deletes — a fourth false docblock, shipping in `dist/` _(verified)_

`src/doc-system/site/orchestrator.ts:367` · `dist/doc-system/site/orchestrator.js:290`

Lines 352–368 (untouched by the diff) still read: _"The mapping is arbitrary but must be STABLE and monotonic — the version's own digits, as a date — so two builds of 1.13.0 agree and 1.13.1 differs."_ The implementation 60 lines below is FNV-1a into a fixed window. Executed: `2.0.0` → 2011-07-26, `1.13.0` → 2012-01-19, `1.12.0` → 2013-10-31, `1.13.1` → 2013-12-20. Not monotonic, not "the version's own digits". ### M3 — The new hash window dates every adopter's ePub into a random past; the committed book claims 2012, a beta lands in 1997 _(verified)_

`src/doc-system/site/orchestrator.ts:430`

Executed against the real module: `1.13.0` → **2012-01-19T15:56:00Z**, `1.12.0` → 2013-10-31, `1.14.0` → 2016-02-16, `1.0.0` → 2007-06-09, `1.13.0-beta.1` → **1997-02-22** (before EPUB existed). `unzip -p docs/tosijs-ui.epub OEBPS/package.opf` confirms the committed, redistributed book carries `2012-01-19T15:56:00Z` — fourteen years before the release. The OPF has no `dc:date`, so this is the **only** date a reader can surface.

This is a regression on two axes, not merely "still synthetic":

- `v1.12.8`'s committed ePub carried `2026-09-01T21:03:40Z` — a real, correct, contemporary date.
- The scheme this diff replaced (2020-anchored ordinal) gave `1.12.0`→2021-12-03, `1.13.0`→2021-12-04, `1.14.0`→2021-12-05 — contemporary _and_ monotone. The new scheme moves `1.12.0`→`1.13.0` **backwards by 22 months**.

Distinctness (unobservable outside the build) was bought by regressing the one property an end reader sees. _(The finding's downstream claims — that Calibre/Apple Books/library ingest sort or replace-if-newer on this field — are mechanism-plausible via the EPUB 3 Release Identifier but were not verified per-system; the verified core stands without them.)_ **Folds in the separately-reported "successive versions move backwards in time" minor.**

**Fix (either is sufficient, both are cheap):** (a) set `epub.modified` in this repo's own `tosijs-site.config.ts` — the option now exists and this repo is its first adopter; and/or (b) anchor the window to a contemporary band (`Date.UTC(2020,0,1) + hash % 6yr`) so the synthetic date is at least in the era of the software. Worth considering the ecosystem-standard answer this function has now missed four times: honour `SOURCE_DATE_EPOCH` when set, hash as fallback. Drop the unsupported "plausible to a reader" and "nothing reads these as a sequence" claims either way.

## Minor findings (5)

### m1 — Distinctness is asserted absolutely in both docblock and CHANGELOG; a 32-bit hash into 15.77M minutes collides — demonstrated _(verified in triage)_

`src/doc-system/site/orchestrator.ts:418-430` · `CHANGELOG.md:19`

_(Deduped: reported as a minor by correctness and as a nit by blast-radius — same defect, kept at minor.)_

The docblock says _"different version STRINGS (prerelease tags included) yield different ones. A hash gives both for any input"_; the CHANGELOG repeats it as a promise. `hash % (30*365*24*60)` has 15,768,000 buckets — a birthday bound, not a guarantee. I ran the shipped function over 38,400 plausible versions (major 0–3 × minor 0–39 × patch 0–39, plain + beta.1/2/3 + rc.1/2): **39 collisions**, e.g. `0.7.12-rc.1` and `0.29.26-beta.3` both → `2009-11-15T14:38:00Z`. The generated sweep in `epub-date.test.ts` is ~1,320 versions and happens to be collision-free, so it **certifies a claim it cannot support** — the fourth absolute claim about this function in one release, and the same shape (a green test read as proof of a universal property) the release notes name as their through-line.

**Fix:** one word. _"deterministic, and collision-resistant — a 32-bit hash over ~15.8M minutes, so two versions share an instant roughly once in 15.8M pairs."_ Same edit in `CHANGELOG.md`. If a guarantee is actually wanted, mix into 2^48 and widen the window.

### m2 — An unparseable `epub.modified` falls back silently, with no diagnostic _(verified in triage)_

`src/doc-system/site/orchestrator.ts:399`

`versionAnchoredDate` gates on `!Number.isNaN(Date.parse(override))` and otherwise falls through to the hash with no warning. Reproduced: `modified: '2026-13-01'` (typo) → silently `2012-01-19T15:56:00Z`, the synthetic date. `modified: '03/09/2026'` (intending 3 September) → silently `2026-03-08T22:00:00Z`, i.e. 8 March. Both land in a committed, redistributed artifact with a green build.

**Fix:** `console.warn` when `override !== undefined` and `Date.parse` is NaN, naming the value and the expected format, before falling back.

## Nit (1)

### n1 — `epubOptionsFor` is typed `Record<string, unknown>` in and out, and its conditional `bookTarget` spread quietly changed precedence _(verified in triage)_

`src/doc-system/site/orchestrator.ts:379` · `dist/doc-system/site/orchestrator.d.ts:29`

The emitted declaration is `epubOptionsFor(epubOpts: Record<string, unknown>, version: string, bookTarget?: unknown): Record<string, unknown>` — so `coverColour` or `modifed` compiles clean through **the very function extracted to make the wiring type-checkable**, and the `as Parameters<typeof buildEpubInChild>[1]` cast at the call site is a no-op.

Separately, the diff confirms a precedence change: the old inline literal ended `...epubOpts, bookTarget,` so the loop variable always won, including when `undefined`; the new `...(bookTarget === undefined ? {} : { bookTarget })` omits the key, so a `bookTarget` present in `epubOpts` would now survive into the default-volume build and bind the wrong volume. Unreachable through the typed `SiteConfig` today — which is why it is a nit — but it is a silent precedence change made by a refactor whose stated purpose was to stop a precedence bug.

**Fix:** `epubOptionsFor(epubOpts: BuildEpubOptions, version: string, bookTarget?: string): BuildEpubOptions`, drop the cast, and keep `bookTarget` unconditional (or comment the omission as deliberate).
