## Blockers (2)

### B1 — `POST /__docstore/source` is CSRF-able: any page the developer visits can write any file under the repo root, including `.git/hooks/*` → local code execution _(security, verified confirmed — issue #90, OPEN)_

`src/doc-system/site/dev-auth.ts:591` — `mayWriteSource`'s direct path is `return isLoopbackAddressForAuth(opts.peer)`: **no credential at all**. `handleWriteSource` (`dev-server.ts:917`) does `request.json()` regardless of Content-Type, so a cross-site `fetch(..., {mode:'no-cors'})` with the CORS-safelisted `text/plain` is a _simple request_ — no preflight, peer is 127.0.0.1, gate passes. `resolveInRepo` only asserts containment under `PROJECT_ROOT`, so `.git/hooks/pre-commit`, `package.json` and `bunfig.toml` are all writable. This repo's own `tosijs-site.config.ts:50` sets `editableSources: true`.

I re-verified independently: `grep -rniE "sec-fetch|origin|csrf|cross-site" src/doc-system/site/{dev-server,dev-auth}.ts` returns **zero code hits** — only the prose comment at `dev-auth.ts:42-45` claiming SameSite=Lax gives "free CSRF protection", which is true only of the _tunnel/session_ path. The default loopback path needs no cookie, so the design's stated defence does not cover its own primary path. `gh issue view 90` → **OPEN**, filed 2026-08-19; `reviews-1.11-pass2.md:178` and `pass3.md:165` both asked for fix-or-disposition; `#90` appears in neither `CHANGELOG.md` nor `TODO.md`.

**This release makes it worse, not neutral.** `POST /__build` (`dev-server.ts:2021`) is a _third_ consumer of the same peer-only gate — body-less, no custom header, therefore also a CORS simple request. An attacker who writes `bunfig.toml`/`package.json`/a watched source via `/__docstore/source` can now _trigger the build that executes it_ without waiting for the developer's next commit. Standalone, `/__build` is DoS-class (each POST drives `rm -rf <outputDir>` + a full build; the `LOOP_STREAK=30` guard bounds it to ~30 builds before the server `process.exit(1)`s with a message blaming your watched files).

**Fix (one shared predicate, three call sites):** in `dev-auth.ts`, beside `isLoopbackAddressForAuth`, add a pure + tested `isSameOriginRequest(request, expectedOrigin)` that refuses when `Sec-Fetch-Site` is present and not `same-origin`/`none`, or when `Origin` is present and does not match this server's origin. Apply it to `POST /__docstore/source`, `POST /__build` and `POST /report` — **in the `!viaTunnel` branch only**, because `UPSTREAM.md:719` records that a blanket cross-site rejection breaks the legitimate tunnel case. Every in-repo caller uses a relative URL (`doc-browser.ts:1221`, `live-example/component.ts:1010`) so sends `same-origin`; the CLI (`orchestrator.ts:241`) sends neither header and is unaffected. Add the refusal test in the shape `/report` and `/__devlink` already have.

**If you will not fix it now**, say so in plain words in the release notes and on #90 — _"`bun start` is loopback-**trusted**, not loopback-safe; do not browse the web with `editableSources: true` running"_ — rather than leaving it silently open for a fourth release. Silence is the thing that is failing here, not the difficulty.

### B2 — The tag would capture generated files that are not the build of their commit _(mechanical release gate)_

`git status` at HEAD (`706ca0ce`) is **dirty**: `docs/tosijs-ui.epub` and `docs/version.json` modified, uncommitted. CLAUDE.md requires generated files to match the source they ship with. Tagging now violates that, and it also falsifies `706ca0ce`'s own commit-body claim that the ePub is byte-identical across rebuilds at a fixed commit. `git describe` = `v1.12.8-18-g706ca0ce`; base ref is correct, and the diff legitimately spans 1.12.9 (committed, never tagged) + 1.13.0.

## Majors (9, all verified)

### M1 — The delegated build's socket dies at 120 s; a _successful_ build is reported as "stop your dev server" and exits 1

`orchestrator.ts:247` sets `AbortSignal.timeout(10 * 60 * 1000)`, but `/__build` (`dev-server.ts:2021`) emits no bytes until the build finishes and `Bun.serve` runs with `idleTimeout: DEV_IDLE_TIMEOUT_SECONDS` = `min(255, DEV_REQUEST_TIMEOUT_SECONDS || 120)` (`dev-server.ts:197`, nothing sets that env var anywhere). Verifier reproduced with the shipped constant: fetch threw _"The socket connection was closed unexpectedly"_ at **120.03 s** while the handler completed fine at 150 s. **The stated budget is unreachable by 5×** (the original finding's "~2× idleTimeout" estimate was optimistic; it is ~1×). `delegateBuild` catches → `null` → `describeHolder` → exit 1 telling the user to kill a dev server that is mid-`rm -rf`-and-repopulate — the exact `#51` damage this feature exists to prevent. Also: `build-lock.ts:73` says in its own words "a legitimate build can take minutes."
**Fix:** stream a keepalive chunk from a `ReadableStream` while the build runs (resets the idle clock, gives the CLI progress), or return `202` + a build id and poll. At minimum align the two numbers and distinguish "could not reach" from "connection dropped mid-build".

### M2 — A delegated build resolves on a build that started _before_ the request, then a queued rebuild starts wiping `docs/` immediately after `bun run build` exits 0

`dev-server.ts:1442` — `buildNow` pushes a waiter then calls `void rebuild()`; if `building`, `rebuild()` only sets `pending = true` (1451) and the waiter is released by the **already-running** build's `finally` (1470), one line before `if (pending) { pending = false; void rebuild() }` (1494) starts a full build whose prologue is `mv docs docs.last-good; mkdir -p docs` (`orchestrator.ts:437-461`) and `rm -rf dist`. Verifiers transcribed the state machine and ran it: build #2's wipe is already underway when the caller is told success. This is the **likely** case (edit a file → watcher fires → run the build; the chokidar handler has no debounce), and the documented next step is `git add dist docs && git commit` — a half-populated committed output tree. The doc comment at 1436 ("the request joins it rather than queueing another"), the commit body of `3461c775`, and `CHANGELOG.md:45` all assert the opposite of what the code does. It gets both wrong halves at once: it pays for the extra build _and_ answers from the earlier one.
**Fix:** release waiters only when `building === false && pending === false`, i.e. the reply means "the tree reflects the latest change and nothing further is queued". Report which build the `ok` refers to (sequence/start time).

### M3 — Both regression tests for this release's two headline fixes assert hand-written copies of the production predicate; deleting either fix leaves the suite green

`src/pocket-bar.test.ts:97` defines `const peeks = (pointerType: string) => pointerType !== 'touch'` **inside the test** and asserts on that local arrow — it never mounts a `<tosi-pocket-bar>`, never dispatches a `pointerenter`, and never touches the symbol it imports. `src/doc-system/site/build-lock.test.ts:236` does the same with `canDelegate`, a verbatim copy of `orchestrator.ts:355`. Verifier ran a **mutation test** in an isolated scratch copy: stripping the `pointerType === 'touch'` guards from both handlers _and_ broadening the delegation predicate to accept `role === 'build'` killed **zero** tests — identical pass/fail sets against a control. Grep confirms no other coverage: `pointerType`/`PointerEvent` appear nowhere else in `*.test.ts`/`*.pw.ts`, and `__build` appears in **no test at all**. Worse, `build-lock.test.ts` carries a comment asserting "the wire behaviour is covered end-to-end by driving a real server" — that test does not exist, and an honest wire test would have caught **M5**. This is the pattern CLAUDE.md records from the 1.9.0 notes (fixes described that were never written).
**Fix:** mount the element and dispatch real `PointerEvent`s; export the delegation predicate from `orchestrator.ts` and import the _real_ one in the test; correct or delete the false coverage comment.

### M4 — `delegateBuild` triggers a destructive build in a process it has not identified, and never validates `holder.port`

`orchestrator.ts:236/356`. `holder` is JSON read from a tmpdir lock file with **no runtime validation** (`port?: number` is compile-time only) and liveness is `process.kill(pid, 0)` alone — EPERM counts as alive (`build-lock.ts:103`), staleness is liveness-only and never age. Verifier reproduced both legs end-to-end: (a) a planted lock naming a live pid + an impostor listener answering `{"ok":true}` made `bun bin/dev.ts --build-only` print **"✅ dev server rebuilt this tree"** and **exit 0** with `docs/` and `dist/` byte-for-byte untouched; (b) `new URL('https://localhost:1@127.0.0.1:8911/__build')` resolves the userinfo form to an off-target host, and Bun's fetch follows it with `rejectUnauthorized:false`. The non-adversarial premise is **already true on this machine**: `$TMPDIR` holds six `tosijs-build-*.lock` files across six project roots, two with dead pids, one of them recording port **8787** — the ecosystem-wide default every tosijs project uses. So `bun run build` in project A can rebuild project B's site (`rm -rf` its outputDir) and report success for a tree nothing touched. Twenty lines away, `killStrayServer` (`dev-server.ts:409-468`) sets the bar for exactly this class: verify `ps -p PID -o comm=`, verify the process's cwd is _this_ project, warn-and-skip when it can't. The new cross-process action meets none of it.
**Fix:** validate `port` is an integer 1..65535 before interpolation; have `/__build` echo `{ok, detail, pid, root}` and refuse unless `pid === holder.pid` and `root === path.resolve('.')` (`LockHolder.root` is already recorded); write the lock 0600.

### M5 — A dev server that predates 1.13.0 answers `POST /__build` with the SPA fallback (200 + index.html), and the new build reports "the dev server's build FAILED" and exits 1

`orchestrator.ts:249`. `isSPA` is unconditionally `true` and the fallback runs for any method on a dotless path, so a v1.12.8 server returns `200 text/html` for the POST. `delegateBuild` special-cases only 404/409, so `res.json()` rejects → `{}` → `body.ok === undefined` → `🛑 the dev server's build FAILED` → exit 1. Verifier reproduced this against a stand-in implementing v1.12.8's fallback verbatim. `build-lock.ts` is **unchanged** in this diff, so the old server writes exactly the holder record the new code delegates to. This is the _normal_ upgrade path for every `tosijs-ui/site` adopter — dev servers here live for days and keep running the code they loaded at launch. `delegateBuild`'s own docstring promises `null` for "answered something this does not understand"; that is precisely the case it misses. Fails closed (nothing corrupted), but replaces an accurate, actionable message with a false accusation pointing at the wrong layer.
**Fix (two lines):** require `content-type: application/json` and `typeof body.ok === 'boolean'` before believing it; otherwise `null` → `describeHolder` plus "the running server predates this endpoint; restart it".

### M6 — Delegation silently substitutes the dev server's launch-time config for the caller's

`orchestrator.ts:354`. `buildSite` is a public export; when the lock is held it hands the work to a server that builds with the `SiteConfig` it was _launched_ with (closed over at `dev-server.ts:1345`) and writes to _that_ config's `outputDir`. The caller's config never crosses the wire. Verifier reproduced in a scratch project: `buildSite({outputDir:'site-prod', baseUrl:'https://prod.example.com'})` printed "✅ dev server rebuilt this tree", **returned `true`**, and `site-prod` was never created (server logged `body bytes=0`). Also skipped: `config.prebuild?.()` and the `docPath`/`outputDir` overlap guard — so the `true` covers a build that ran none of the caller's hooks. The lock is keyed on project _root_, not `outputDir`, so two configs writing to different trees (which do not actually race) collide and now silently substitute. The previous refusal was honest about this.
**Fix:** send the caller's resolved `outputDir` (ideally a config fingerprint) with the POST; `/__build` answers 409 on mismatch. Pair with the opt-out in F10.

### M7 — `collapseWidgetsAfterAction` writes `bar.open = false` behind `TosiPocketBar`'s back, desyncing the private `pinned` flag — the bar sticks open, and the next handle tap is dead

`src/live-example/component.ts:1619`. `pinned` (`pocket-bar.ts:137`) is private and mutated only by `toggle()`/`handleOutsidePointer`. Verifier drove the real component: click handle (pinned=true, open=true) → click a slotted control (open=false, **pinned still true**) → hover in (open) → hover out → **stays open** over the just-maximized example, because `handlePointerLeave`'s `!this.pinned` guard never fires. That is the exact regression the change set out to remove, in a stickier form. `handleFocusOut`'s guard is dead for the same reason. **Understated in the original:** the next handle click is also _dead_ — `toggle()` flips `pinned` to false then `setOpen(false)` on an already-closed bar — and the sibling touch fix in this same release (`63908177`, `pointerenter` early-returns for touch) means every post-action tap on touch is dead with no hover path to mask it. This is the highest-reach chrome in the library: every live example on every page of every `tosijs-ui/site`.
**Fix:** give `TosiPocketBar` a public `close()`/`dismiss()` that clears `pinned` and calls `setOpen(false)` (or make `open` authoritative with `pinned` derived), and call that. Also drop the dead `if (bar === undefined || bar === null) return` — `this.parts` throws rather than returning nullish.

### M8 — The published TypeScript surface changed for every consumer, and the CHANGELOG gives the wrong reason for the peer floor

Verified by me: `dist/router.d.ts` `XinProps` → `TosiProps`, `dist/theme.d.ts` `XinStyleSheet` → `import("tosijs").TosiStyleSheet`, same in `localize.d.ts`/`live-theme.d.ts` — with no source change. The shipped `.d.ts` now **hard-requires** a tosijs exporting `TosiProps`/`TosiStyleSheet`; that, not the security fix and console-warning cleanup, is the real reason the peer floor must narrow to `^1.9.1`. Nobody type-checked the emitted declarations against the declared floor or against 1.8.x to establish what an adopter actually sees. Related, unreviewed: narrowing `^1.7.8` → `^1.9.1` drags a 1.7.x adopter through **tosijs 1.8.0**, which this repo's own CHANGELOG (~line 1106) records as _"deviates from semver and says so"_ — it removed `data-ref` and `<xin-slot>`. The 1.13.0 notes do not mention this or link the tosijs 1.8.0 notes.
**Fix:** state the real cause in the CHANGELOG, add a migration line pointing at tosijs 1.8.0's removals, and have `test-consumer` type-check the emitted `.d.ts` against the _declared floor_, not the devDep-resolved version.

### M9 — `versionAnchoredDate()` cannot reach a fixed point on a release commit _(minor severity as filed; elevated because it is the direct cause of B2)_

`orchestrator.ts:272`. Anchoring to `git log -1 --format=%cI -- package.json` narrows the "commit → build → dirty → commit" loop but does not close it: the release flow _always_ touches `package.json`, and at build time the anchor still returns the **previous** release's commit — so the shipped ePub carries a stale date and the first rebuild after the release commit re-dirties `docs/`. HEAD demonstrates it live (see B2). _(unverified detail: the per-volume `await versionAnchoredDate()` also sits inside the `for (const bookTarget of volumes)` loop at line 1221, shelling out `git log` N or 2N times per build including every watch rebuild — hoist it.)_
**Fix:** anchor to something that exists before the commit — the `version` string mapped to a fixed date, or an explicit `epub.modified` the release sets.
