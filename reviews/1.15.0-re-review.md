## Lens: Blast radius (what propagates outside the repo — cost or benefit)

### [BLOCKER] `dist/iife.js` now inlines prismjs (MIT), and NOTICE — the file that exists for exactly this — never mentions it
`NOTICE:79`

Verified from the sourcemap: `JSON.parse(dist/iife.js.map).sources` lists 28 prismjs inputs (`prism.js` + 27 `components/prism-*.js`, ~162KB of raw source) inlined into `dist/iife.js`. `grep -ci prism NOTICE` → 0; `grep -c 'Lea Verou' dist/iife.js` → 0; LICENSE and README mention neither. Prism's MIT licence requires "The above copyright notice and this permission notice shall be included in all copies or substantial portions of the Software", and this repo's NOTICE states its own purpose in those words — "`dist/iife.js` inlines its dependencies … the attribution below travels with the iife and with anything built from it" — and already carries entries for tosijs, marked, Feather Icons and CodeMirror (also MIT). Every party who serves `docs/iife.js` redistributes Prism without attribution: ui.tosijs.net, every CDN `<script>` user, and every `tosijs-ui/site` adopter without `bundleEntry` (the iife is the default page script). This is an obligation that propagates to downstream redistributors who have no way to know they incurred it, and it was not raised by the 1.15.0 review.

**Recommendation**: Add a Prism entry to NOTICE's THIRD-PARTY section in the same shape as the CodeMirror one (`Prism — https://prismjs.com/`, MIT, Copyright (c) 2012 Lea Verou, reproducing the permission notice from `node_modules/prismjs/LICENSE`), noting that core plus the 27 grammar modules are bundled into the iife and not into the ESM build. Re-review scope: Tier 0 only — mechanical file addition.

### [MAJOR] prismjs was promoted from optional peer to a hard runtime `dependency`, and nothing adopter-facing says so — the CHANGELOG says a button-importing app "ships none of it"
`package.json:193`

`dependencies` now carries `prismjs: ^1.30.0` (previously `peerDependencies` + `peerDependenciesMeta.optional`). Every consumer of tosijs-ui — including one that only imports `<tosi-rating>` — now installs prismjs into their lockfile, their `bun audit`/Dependabot surface and their licence surface. The commit body records this as a `[change]` bullet, but the published CHANGELOG never does: its only weight statement is line 209, "Prism is a **lazy chunk**: an app that imports a button ships none of it" — true about *bytes*, and read as a whole it invites exactly the wrong inference about *install*. An adopter discovers the new dependency when an advisory against a Prism grammar regex fails their gate, not when they read the release notes. CLAUDE.md's #58 entry records precisely this cost class in writing for the 12 CodeMirror packages and calls it an accepted, documented tradeoff; the equivalent record for prismjs exists nowhere (`grep -i prism TODO.md UPSTREAM.md` → nothing; CLAUDE.md still says the CodeMirror packages are "the **only** hard runtime `dependencies`", which is now false). The prior review's follow-up list asked for this entry and it was not written.

**Recommendation**: Add a CHANGELOG paragraph stating plainly that prismjs is now a real dependency (not optional), why the static-map fix forced it — a literal `import('prismjs')` must resolve at bundle time — and what it costs an adopter (one lockfile entry, one audit surface, no bytes unless something highlights). Mirror it in CLAUDE.md's "Key Dependencies" beside the #58 note, and correct the "only hard runtime dependencies" sentence. Re-review scope: Tier 0 (docs) — no code change implied.

### [MAJOR] The iife grew +31.8KB gzip (+7.3%) since v1.14.1 — above the project's own gate for a new runtime dep, self-identified, undisclosed, and the named remedy is recorded only in a commit body
`src/doc-system/highlight.ts:143`

Measured here: `git show v1.14.1:dist/iife.js | gzip -c | wc -c` = 435,678 → HEAD 467,485 (+31,807 B gzip, +7.3%; raw 1,385,177 → 1,480,110). The B1 fix is what moved it — the static `GRAMMARS` map inlines 27 grammar modules plus Prism core (~162KB of raw source per the sourcemap) into an artifact that cannot code-split. The mid-cycle review measured +10,155 B gzip and graded it an unverified minor; the remediation roughly tripled it, and the number has not been re-stated anywhere. CLAUDE.md sets the gate explicitly: "The gate on a new runtime dep here is the printed gzip delta, not the dependency count." The commit body for f74d39ba8 says so itself — "+30.5kb gzip on the iife is above the 'printed gzip delta' gate CLAUDE.md sets for a new runtime dep. Capping the grammar map smaller is available and unmeasured" — and that sentence is the only place it lives: TODO.md has no prism entry, so tagging evaporates it. The cost lands on every CDN `<script>` user and every `tosijs-ui/site` adopter without `bundleEntry` (the iife is their default page script), on every page load, and it compounds #120 (CodeMirror already ~94% of this bundle).

**Recommendation**: Either measure the capped map (the corpus-realistic set is far smaller than 27 — the build already knows which grammars the corpus uses) or explicitly accept the delta, and in either case (a) state the number in the CHANGELOG where iife/CDN consumers will see it, and (b) put the unexplored remedy in TODO.md with the #120 cross-reference so it survives the tag. Re-review scope if the map is capped: correctness + blast-radius over the remediation diff only (a capped map must not silently stop highlighting a language the corpus uses).

### [MAJOR] The 13 Prism token rules are a structural twin, and B2's fix made the two copies byte-identical — destroying the recorded justification for keeping them apart
`src/doc-system/book-html.ts:72`

The token palette is declared twice: `doc-system-styles.ts` (themed, every colour a `varDefault`) and `DEFAULT_BOOK_CSS` in `book-html.ts:87-99` (raw CSS literals). The prior review graded this an untested structural twin and recorded the *differing values* as an acceptable keep-decision. After B2 the values are identical in all eleven colour rules (#5c6f5c, #666, #a03030, #0b7285, #0a5bb5, #7a4b00, #444, #0a6b52, #2a5db0, #b02020, #2a6b2a) — so the stated reason for the duplication is now false, and the comment above it ("a LIGHT palette, deliberately distinct from the site's") asserts a distinction that no longer exists. The propagation cost is asymmetric and lands where it is least recoverable: the new contrast test (`doc-system-styles.test.ts`) reads only `docSystemStyleSpec()`, and `grep -rn DEFAULT_BOOK_CSS` shows the only test touching the book CSS asserts `white-space: pre-wrap` — so the untested copy is the one that reaches the ePub and print, which is the artifact this release's own argument calls permanent ("a wrong token colour is cosmetic on the web and permanent in a printed book"). Concretely: add a token type, or fix a colour, and it lands on the site and silently not in the book; and an adopter who overrides `--token-keyword` (the whole point of the `varDefault`s) gets a re-themed site and an unchanged book, because the book copy has no override seam at all.

**Recommendation**: Export the selector→colour list from one module and have `DEFAULT_BOOK_CSS` render it (or, minimally, assert in a test that the two selector sets and colour values agree, and run the same contrast check against #f6f8fa for the book copy). If the twin is kept, replace the now-false "deliberately distinct" comment with an explicit, dated keep-decision naming what may diverge. Re-review scope: correctness + blast-radius over the remediation diff only.

### [MINOR] `registerGrammar` ships as a frozen public seam for tjs-lang with no issue filed and no UPSTREAM.md entry — the workaround (`tjs → javascript`) stays, silently, in printed books
`src/doc-system/highlight.ts:75`

`registerGrammar` is exported from `tosijs-ui/site`, documented in the CHANGELOG and in the source comment as the seam for tjs-lang's generated TJS Prism definition (#155), and its entire justification is that a wrong token colour is "permanent in a printed book" — TJS's `greet(name: 'Alice')` colons are values and render with TypeScript's type colour. Until tjs-lang publishes a grammar, `grammarFor('tjs')` returns `javascript` and a test pins that stopgap, so this release ships the exact mis-colouring the feature exists to prevent, in the permanent artifact. `grep -i prism UPSTREAM.md TODO.md` returns nothing: no issue is filed against tjs-lang, and UPSTREAM.md — the file this project keeps for exactly this — has no entry, so the whole cross-package contract (grammar object shape, registration-before-build ordering, whether a registered grammar reaches the build pass and the ePub as documented) is unexercised and the signal is buried in a CHANGELOG paragraph the other repo will never read. The prior review asked for this and it was not done.

**Recommendation**: File the ask on tonioloewald/tjs-lang naming the seam (`registerGrammar(name, grammar)` from `tosijs-ui/site`) and the missing piece (a published Prism grammar object for `tjs`/`ajs`), with the `grammarFor('tjs') → javascript` stopgap as the motivating evidence; mirror it in UPSTREAM.md with the issue URL, and note in TODO.md that the stopgap is removed when the grammar ships. Do not edit the tjs-lang repo. Re-review scope: Tier 0 only.

### [MINOR] The shipped "prismjs not found" console warning still calls Prism an optional peer and tells adopters to `bun add -d prismjs`
`src/doc-system/highlight.ts:250`

The catch block around `await import('prismjs')` still carries the comment "Prism is an OPTIONAL PEER" and prints `'prismjs not found — static code blocks will not be syntax-highlighted (site, ePub and print alike). Install it: bun add -d prismjs'`. Prism is now a hard `dependency`, so the message is wrong on both halves: the condition should be near-impossible, and if it does fire (a broken install, a bundler externalising it), `bun add -d` — a *dev* dependency — is the wrong remedy for a consumer whose shipped build needs it to resolve. This text ships in `dist/` and is the only thing an adopter sees at the moment they are debugging; it propagates a stale claim into their terminal and into whatever they then do to their package.json. Same class as the stale `book-html.ts` "deliberately distinct" comment.

**Recommendation**: Rewrite the message and the comment for a hard dependency ("prismjs failed to resolve — it is a dependency of tosijs-ui; check your install or your bundler's externals"), or delete the fallback if it can no longer be reached by a supported configuration. Re-review scope: Tier 0 only.

### [MINOR] *(severity uncertain)* The highlighter unconditionally overwrites the page-global `Prism` and writes registered grammars into the shared `Prism.languages`, with no documentation and no opt-out
`src/doc-system/highlight.ts:230`

`ensureGrammar` does `sc.Prism = { ...(sc.Prism ?? {}), manual: true }` on BOTH `globalThis` and `window` before importing Prism, and `registerGrammar` later does `prism.languages[lang] = supplied`. Both write state owned by the consumer's page, not by us. On a page that already uses Prism (a docs site embedding `<tosi-highlight>`, a blog with a Prism theme), the consumer's `window.Prism` object identity is replaced by a shallow clone and `manual` is forced true — so if our import happens to run first, their expected auto-highlight never runs and nothing says why; and `registerGrammar('markdown', …)` replaces the grammar for their entire page, not just our blocks. Criterion 4 (never clobber a deliberate choice) and criterion 5 (reversible, with an opt-out documented where the affected person will see it) are both unmet: the behaviour appears in no doc, the component's own docs, or the CHANGELOG. The blast radius is bounded by the page rather than the machine, which is why this is a minor rather than a blocker — but it is a library writing over a global it does not own. Carried over unaddressed from the 1.15.0 review.

**Recommendation**: Set `manual` only when no `Prism` already exists, never replace an existing object (mutate `manual` on it instead, or accept that theirs already loaded), and document both this and `registerGrammar`'s page-global effect in `highlight-block.ts`'s doc comment where an adopter will see it. Re-review scope: correctness + blast-radius over the remediation diff only.

### [MAJOR] *(severity uncertain)* The client highlight pass hardcodes policy 'auto', so an `opt-in` site loses syntax highlighting on client-side navigation
`src/doc-browser.ts:1148`

`highlightBlocks` gained a new `isLiveFence(lang, mode, policy)` filter in this diff, but the doc-browser calls it with only `liveExampleTag`, so `policy` falls back to `'auto'`. With `liveExamples: 'opt-in'` (new in 1.15.0, the setting for prose/book sites), a page of plain ```js fences hard-loads highlighted — generate-site.ts:304 correctly passes `config.liveExamples` to `highlightHtml` — and then loses every token the moment the reader navigates away and back in-page: the doc-browser re-renders the markdown client-side, the blocks are plain, and `isLiveFence('js', undefined, 'auto')` returns true so all six executable languages are skipped. That is B1's exact symptom (531 tokens on hard load, 23 after one client-side nav) reintroduced for the opt-in audience, and it is a regression caused by the new filter: before it, the only gate was `closest('tosi-example')`, and under opt-in `insertExamples` never wraps those blocks. generate-site.ts:302 asserts in a comment that this is "The SAME policy the client will apply" — the client applies a different one. Uncaught because this repo's own site is 'auto' and tests/highlight.pw.ts only exercises that mode.

**Recommendation**: Pass the policy the client actually has: `highlightBlocks(docContent, { liveExampleTag, policy: examplePolicy() })`, using the existing `examplePolicy()` in src/live-example/insert-examples.ts, which reads the same `globalThis.__TOSI_EXAMPLE_POLICY` the build stamps (orchestrator.ts:1325) and is what `insertExamples` itself consults. Add coverage for the opt-in path (a unit test over `highlightBlocks` with policy 'opt-in' is enough). While there: `examplePolicy`/`setExamplePolicy` are not re-exported from src/live-example/index.ts, though insert-examples.ts's own comment tells embedding consumers to call `setExamplePolicy`.

### [MINOR] *(severity uncertain)* The Print-as-PDF path no longer waits for the popup's `load` event before calling `print()`
`src/doc-system/doc-system.ts:386`

`autoPrint: true` used to inject `addEventListener("load", () => setTimeout(print, 300))` into the book document (book-html.ts:207), so printing waited for the popup's subresources. The M1 fix switched to `autoPrint: false` and prints from the parent on a fixed `setTimeout(..., 300)` after `highlightBlocks` resolves. On a doc site, grammars are usually already loaded in the parent page, so `highlightBlocks` can resolve almost immediately and the print dialog opens ~300ms after `document.close()` — before the images and fonts of a whole-corpus book have loaded. The user gets a PDF with blank image boxes and pagination computed against unloaded content. The whole print path has no test of any kind (no unit, no Playwright), so neither the M1 fix nor this regression is observed by any lane.

**Recommendation**: After the highlight pass, wait for the document: `if (win.document.readyState === 'complete') win.print(); else win.addEventListener('load', () => setTimeout(() => win.print(), 300))` — restoring the wait the injected script provided, on top of the new highlight wait. Also guard `win.print()` for a popup the user closed in the meantime.

### [MINOR] The cache-stamp hash still skips a named-but-missing input silently — M3 fixed the ordering, not the mechanism that hid it
`src/doc-system/site/orchestrator.ts:1505`

`stampInputs` names the hydrate bundle, the iife and `doc-system.css`, and the loop does `if (!(await file.exists())) continue` with no output. That silence is exactly what let `doc-system.css` sit in the list while never being hashed, for the life of the feature — the `?v=` equalled sha256(hydrate + iife) and a theme-only change deployed new CSS under an unchanged URL (#151). The remediation moved the `generate-css` call ~80 lines earlier, which is statement placement inside a 1700-line function that nothing asserts. Any future reorder, or a build where the hydrate bundle failed to copy, silently reproduces the original defect: new bytes served under an old stamp, invisible until someone reports "my change had no effect".

**Recommendation**: Make a missing stamp input loud — the list is code-controlled, not user data, so `console.warn` naming the path (or a throw) is appropriate and costs nothing when everything is present. Optionally add a test that a theme-only change moves the stamp, which is the property the fix claims and currently verifies by hand only.

### [MINOR] The new contrast instrument duplicates the background literals, so the public `theme.codeBg` knob is unguarded — and every token fails AA when it is set
`src/doc-system/doc-system-styles.test.ts:143`

`LIGHT_BG = '#fdfdfd'` / `DARK_BG = '#020202'` are hardcoded in the test rather than read from the stylesheet, while `codeBg` is a documented `DocSystemTheme` knob (doc-system-styles.ts:39, `_codeBg: theme.codeBg ?? '#fdfdfd'`). Measured with `theme: { codeBg: '#1e1e1e' }`: operator #444444 → 1.71:1, function #7a4b00 → 2.25:1, string #a03030 → 2.35:1, punctuation #666666 → 2.90:1, comment #5c6f5c → 3.08:1 — every token type below AA, in light mode, which is B2's failure one level up. The test keeps passing because it measures a literal instead of the background the palette sits on, and src/highlight-block.ts:30 ships the claim that each palette is "contrast-checked against the `--code-bg` it actually sits on", which holds only for the default theme.

**Recommendation**: Read the backgrounds out of the spec being measured (`spec[':root']._codeBg` and `spec['.darkmode']._codeBg`) so a theme change fails the assertion rather than sliding under it, and either derive the token palette from `vars.codeBg` or state in the docs that overriding `codeBg` requires overriding the `--token-*` set.

### [MINOR] *(severity uncertain)* Test-only examples hide `.preview`, silently changing the environment their tests run in
`src/live-example/styles.ts:253`

`:host(.-test-only) .preview { display: none }` now applies to any example whose only fence is ```test — but `preview` is still injected into the test block's scope, and this repo's own system-level CSS canary (src/live-theme.ts, the second test-only example in the corpus) appends nodes to `preview` and measures them. **Recommendation**: Say it in the new `A test-only example shows its results` doc section and in the `isTestOnly` JSDoc: the preview is removed from layout, so a test-only example must not measure layout. If layout-capable test-only examples are wanted, contain the preview off-screen (zero height + overflow hidden) instead of `display: none`. Before shipping, run the doc-test lane and confirm the live-theme CSS canary is still green — it is the corpus's system-level styling signal and this change landed after the last recorded run.
