## Blockers — fix before `git tag`

### BLOCK-1 · `epub.modified` is clobbered by the spread that follows it *(verified — confirmed by two lenses independently, reproduced here)*
`src/doc-system/site/orchestrator.ts:1335`

```ts
await buildEpubInChild(config, {
  modified: versionAnchoredDate(version, (epubOpts as {modified?: string}).modified),
  ...epubOpts,          // ← re-sets `modified` from the raw config, discarding the sanitized value
  bookTarget,
})
```

`epubOpts` **is** `config.epub`, so if the adopter set `epub.modified` the spread wins. Reproduced against source and the committed `dist/`:

- `epub: { modified: '2026-09-03' }` → builder receives `"2026-09-03"` (should be `2026-09-03T00:00:00Z`)
- `epub: { modified: 'not a date' }` → builder receives `"not a date"` (should be the synthetic fallback)

`epub-cli.ts` forwards `opts` verbatim; `epub.ts:787` only strips fractional seconds, then interpolates straight into `<meta property="dcterms:modified">` (`epub.ts:390`). EPUB 3 requires exactly `CCYY-MM-DDThh:mm:ssZ` — so the **obvious spelling of a brand-new option silently emits an ePub that EPUBCheck rejects and Apple Books / Kobo / Google Play refuse at ingest**, in a committed, redistributed artifact, on first use.

`epub-date.test.ts`'s "an unparseable override falls back rather than emitting garbage" passes because it calls `versionAnchoredDate` directly and never crosses the wiring that throws its return value away.

This repo's own `tosijs-site.config.ts:46` sets no `modified`, so `docs/tosijs-ui.epub` is unaffected — the blast radius is scoped precisely to adopters of the option this release announces.

**Fix:** move the key after the spread — `{ ...epubOpts, modified: versionAnchoredDate(version, epubOpts.modified), bookTarget }` — and add one test that drives the **option-assembly path**, asserting the value handed to the builder for `'2026-09-03'` and `'not a date'`.

### BLOCK-2 · `Origin: null` is explicitly allowed, reopening #90 for the population the fix names *(verified — confirmed by two lenses; predicate executed)*
`src/doc-system/site/dev-auth.ts:633`

```ts
if (origin !== null && origin !== 'null') { /* …compare host… */ }
return true
```

Without the `&& origin !== 'null'` term, `new URL('null')` throws and hits the existing `return false // an Origin we cannot parse is not one we can accept`. The literal is therefore an **explicit, undocumented, untested exemption** for the one Origin value an attacker can choose cross-site. Executed against the real module:

| headers | result |
|---|---|
| `{ origin: 'null' }` (no fetch metadata) | **true** |
| `{ origin: 'null', 'sec-fetch-site': 'cross-site' }` | false |
| `{ origin: 'https://evil.example' }` | false |
| `{}` | true |

`Origin: null` is what `<iframe sandbox="allow-scripts allow-forms">`, `srcdoc`, `data:` and cross-origin-redirected POSTs send. Modern engines stay protected only because they *also* send `Sec-Fetch-Site: cross-site`. The unprotected set is exactly the one the new comment names as its reason for existing — Safari < 16.4, Firefox < 90, older WKWebViews — all of which support sandboxed iframes and none of which have Private Network Access gating. The mkcert CA makes the TLS hop to `https://localhost:8787` clean.

The chain downstream is intact: `mayWriteSource`'s direct path is `isLoopbackAddressForAuth(peer)` only, `handleWriteSource` (`dev-server.ts:948`) does `await request.json()` with **no Content-Type check** (so `text/plain` keeps it a simple, preflight-free request), and `resolveInRepo` accepts any path under the repo root — `.git/hooks/pre-commit` included. This repo's `tosijs-site.config.ts:50` sets `editableSources: true`. The response is CORS-blocked; the write is not.

`dist/doc-system/site/dev-auth.js:529` carries the identical clause, so it ships.

Grep for `srcdoc|sandbox=` across non-test `src/` returns **zero** — nothing this project ships makes a request from an opaque origin, so no legitimate caller depends on the exemption. The CLI and `curl` send *no* Origin header (the `origin === null` branch), which is untouched.

Lenses rated this **major** (dev-only, needs `editableSources` plus an affected engine). It is release-gating here because it is the same class as the MAJ-2 it was written to remediate, on the endpoint this release **headlines as fixed**, and the fix is deleting five characters.

**Fix:** drop `&& origin !== 'null'` so an opaque origin falls into the existing unparseable-origin refusal. Add the sandboxed-frame case to `dev-auth.test.ts` beside the existing Origin tests. Either restore the deleted `mode === 'no-cors' && site === null` clause or record why it was dropped — note it was practically inert (no engine sends `Sec-Fetch-Mode` without `Sec-Fetch-Site`), so its removal loses nothing real.
