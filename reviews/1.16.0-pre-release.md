## Blockers

### B1: Sanitized `<tosi-md>` is bypassed by a nested `<tosi-md sanitize="off">` (security, verified)
`src/markdown-viewer.ts:174`

Untrusted value that triggers it:
```
hello

<tosi-md sanitize="off">&lt;img src=x onerror="window.__pwned=1"&gt;</tosi-md>
```
kilpi deliberately keeps unknown custom elements, so the inner `<tosi-md sanitize="off">` survives sanitizing. When it connects, it decodes its own `textContent` and takes the `mode === 'off'` branch, which does `this.innerHTML = html`. The result is a live `<img onerror>` in the DOM (reproduced in happy-dom). A `src="https://attacker/…"` on the nested element takes the same path, with the payload fetched from the attacker. Other elements probably work the same way (not verified by the skeptic): `<tosi-example>` runs its child `<pre>` code, and `<tosi-doc-system docs=…>` loads attacker-chosen docs. The 1.16 `[break]` CHANGELOG entry says this class of attack is now closed, and `HOSTILE` in `markdown-viewer.test.ts` has no nested custom-element vector.

**Fix:**
- Before `replaceChildren`, neutralise the tosijs-ui elements that execute content, inside the sanitized template.
- A `<tosi-md>` must not honour `sanitize="off"` when it has a sanitizing ancestor `<tosi-md>`. Alternatively, strip `sanitize` (and `src`, if remote fetches are unwanted) from nested `tosi-md` elements.
- Strip `tosi-example` and `tosi-doc-system`, or remove their code-bearing children.
- Add these vectors to `HOSTILE`, plus a test that checks `residue()` after the *nested* element has connected and rendered.
- Document that custom elements which survive sanitizing are trusted to render their own content safely.

**Re-review scope:** security and correctness over the remediation diff, plus an adversarial sweep for other tosijs-ui elements that read their children or attributes as markup or code.

### B2: #191 missing from the 1.16.0 CHANGELOG while `release-check` is green (correctness, verified)
`CHANGELOG.md:3`, `src/doc-system/release-notes.ts:202-234`

Commit `cd3a04e01` carries an adopter-facing `[fix]` that tells readers to rebuild their site. `grep 191 CHANGELOG.md` finds nothing. `bun run release-check` still prints "4 annotation(s) since v1.15.5, all accounted for" and exits 0. The cause: `uncovered()` matches 3-word runs against the *whole* changelog. The only hits for this bullet ("code split chunks", "rebuild your site") come from older sections. The 2736cd4a peer-floor `[break]` bullet reportedly also matched only older text (not re-probed).

**Fix now (release-blocking):** write the 1.16.0 entry for #191. It must say:
- The ESM entry is now `hydrate-<hash>.js`, with no `?v=` query.
- Anything that references `hydrate.js` by name has to follow the rename: CSP/SRI entries, preloads, host cache rules, service workers, smoke checks.
- Adopters must rebuild their sites.

While writing notes, also re-check that the 2736cd4a `[break]` is actually covered in the 1.16 section.

**Follow-up (non-blocking):** scope `uncovered()`'s haystack to the section for the version being released.

**Re-review scope:** Tier 0 for the CHANGELOG entry. Correctness over the `release-notes.ts` diff only.

## Completeness gaps (must be closed before tagging)

1. **The diff reviewed is not the diff that will ship.** `package.json` and `src/version.ts` still read 1.15.5, and `bun bin/release-notes.ts` prints the new notes under `## 1.15.5`. After the bump and rebuild, re-diff at least `dist/*.d.ts` and `dist/iife.js`.

3. **Adopter blast radius of the #191 filename change** was not assessed beyond the nit above. Check the emitted `.d.ts` and `doc-site-system.md` for any promise of `hydrate.js`, and verify the 8-character hash assumption in the Caddyfile.
4. **The sanitize-by-default change was not checked against real consumers.** `../loewald-dot-com/src/blog.ts:460` and `src/page.ts:39` call `markdownViewer({...})` without `sanitize`, and the blog runs `LiveExample.insertExamples`. Embedded `<iframe>`, `<style>`, `<script>` or `<form>` will now be stripped silently. `elements: true` mode (whose stated purpose includes forms) is also sanitized by default. Decide which consumers need `sanitize="off"`, and say so in the migration note. Do not edit loewald-dot-com from here; file it there.
5. **Type surface of the tosijs 1.10 `withAttributes` migration (37 classes)** has not been verified. Check for TS2742 or non-portable types in `dist/*.d.ts`, for adopter subclasses overriding `static initAttributes`, and for the typing of the `xin*` aliases. Run `bun run test-consumer` plus a consumer `tsc` against the packed `.d.ts`. "Nothing changes at runtime" has not been independently verified.
6. **CDN behaviour change:** the iife inlines tosijs-schema 1.8.0 → 1.10.2 (only a `[note]`). Assess the validation differences for CDN users and add a CHANGELOG line and a NOTICE entry.
7. **Single CodeMirror instance** (`de4077a7a`) has not been verified against the rebuilt `dist/iife.js.map` `sources` or against a clean consumer install. Read the sourcemap; do not grep the bundle.
8. **Contributor repo config** (`virta` hooks and `.mcp.json`): covered by the follow-up above. The security lens did not assess it.
