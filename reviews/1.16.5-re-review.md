## Minor findings

### M1. A patch changes what the `pinnedTopRows` / `pinnedBottomRows` getter returns (correctness, **verified**)
`CHANGELOG.md:41`. The change came in f193e7374 and ships in 1.16.5. In v1.16.4 the getter returned `undefined` when unset, typed `any[] | undefined`. At HEAD it returns `this._pinnedTopRows ?? null`, typed `any[] | null`. Adopter code that checks `=== undefined` silently stops taking its branch, and TypeScript gives no warning. This breaks the project's rule that "a patch never breaks you". The CHANGELOG states the change accurately, but it is buried in a paragraph about list-binding warnings. The practical risk is small, since `== null` checks and truthiness checks still work.
**Decide one of two ways:**
- (a) Accept it as a deliberate, documented exception, and move the "Reading it changes too" sentence to the top of the 1.16.5 notes. This needs a Tier 0 re-review only.
- (b) Keep the getter returning `undefined` and fix the creator path another way. This needs a correctness + blast-radius re-review.

### M2. The type that would have caught B1 is still open; narrowing it is free only until 1.16.5 publishes (blast-radius, unverified)
`src/float.ts:119` types `TosiFloat.anchorPosition` as `string | null`, and `src/pop-float.ts:451` casts it back with `as FloatPosition | undefined`. So storing a CSS position string there (the B1 shape) still type-checks. `anchorPosition` is new since v1.16.4 and is not in any tag yet, so narrowing it now costs consumers nothing. Once it ships as `string | null`, narrowing it becomes a change at the type level.
**Recommended before tagging:** type it `FloatPosition | null` and drop the cast. This needs a correctness re-review of that diff only. `@typescript-eslint/no-shadow` would also catch this class, but it is not cheap to switch on: 69 hits repo-wide.

### M3. The #2460 refit unit test passed while B1 was present (correctness, unverified)
`src/pop-float.test.ts:181`. "When Safari's toolbar shrinks the visible area…" asserts only the `--max-height` delta, so it passes against the pre-fix `pop-float.ts`. Only the new B1 test fails there. Every earlier green result for #2460 therefore came from a test that could not see this bug. That probably includes any on-device check behind the CHANGELOG line "Menus stay inside the screen on iPhone", if that check was done before 8526e8f7d.
**Action:** re-check #2460 on a real iPhone with the fixed build, changing the visible viewport (toolbar, keyboard or zoom) while a menu is open. Run `bun playwright test tests/menu-mobile.pw.ts --project=chromium --project=webkit`. Also assert `float.style.top` / `anchorPosition` in the older "room shrinks" test, so it cannot pass vacuously again.
