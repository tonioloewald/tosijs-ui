## Blockers (must fix before tag)

### B1 — `buildNow`'s quiescence loop re-queues a build every iteration and never terminates

`src/doc-system/site/dev-server.ts:1443-1465` — **confirmed, reproduced independently in this triage.**

```js
for (;;) {
  const done = new Promise((resolve) => buildWaiters.push(resolve))
  void rebuild()                      // <- re-arms on EVERY iteration
  await done
  if (!building && !pending) break
}
```

The ordering in `rebuild`'s `finally` (line 1486+) is what makes it deterministic, not racy: `buildWaiters.splice(0).forEach(resolve)` only _schedules_ microtasks, then `if (pending) { pending = false; void rebuild() }` runs **synchronously** and sets `building = true` before the waiter's continuation. So `buildNow` always wakes with `building === true`, fails the break, loops, and calls `rebuild()` again — which sets `pending = true`, guaranteeing the next cycle too. The invariant re-establishes forever.

I transcribed lines 1428–1519 into a standalone script and ran both shapes:

- **idle** → `iterations: 1, builds: 1` (correct — this is why it hides)
- **contended** (a watch rebuild in flight when `/__build` arrives) → loop detector fires at `streak = 30, builds = 31`, then keeps going; my 200-iteration bail-out stopped it

**Trigger is ordinary.** The chokidar handler (line 1549) calls `rebuild()` with **no debounce**, so a _single_ save under `src/`, `README.md`, `demo/src`, `icons/` or any adopter `docPaths`/`staticDirs` during the delegated build is sufficient. `buildNow` exists only inside the watch block — the loop is reachable exactly in the case delegation exists for.

**End state:** the developer's long-lived dev server `process.exit(1)`s with a diagnostic blaming _the user's watcher config_ ("a build that writes a file it also watches") plus a top-triggers list naming innocent files; ~30 full site+bundle builds are burned; `bun run build` fails. At ~3s/build the server usually dies **before** the client's 115s `AbortSignal.timeout`, so the CLI reports "could not reach the dev server" rather than a timeout. The tree is not corrupted (`delegateBuild` returns `null` and the caller refuses rather than racing), but the M2 remediation traded a narrow race for a guaranteed failure.

**Ships to adopters:** present verbatim at `dist/doc-system/site/dev-server.js:1262`, which is the published `tosijs-ui/site`.

**Falsifies:** `CHANGELOG.md:115` ("**It waits for the tree to settle**"), the `[fix] M2` bullet in `0314e343`, and the delegation section of `src/doc-system/doc-site-system.md`.

**Fix:** hoist the re-arm out of the loop — `void rebuild()` on the first iteration only; subsequent iterations just park a waiter. Or move `buildWaiters.splice(0).forEach(resolve)` _below_ the `if (pending)` block so a queued build keeps the waiter parked. Add an iteration cap (~5) returning `{ ok: false, detail: 'tree never settled' }` so a genuinely churning watcher degrades to a message, not a build storm.

**Mandatory test:** the `building`/`pending`/`buildWaiters` trio is pure and testable without a server. Cover both contended orderings (rebuild-already-in-flight, and a watcher event during the delegated build). Nothing in the suite touches `buildNow` today.

**RE-REVIEW SCOPE after remediation:** correctness + blast-radius over the `dev-server.ts` build-queue diff and its new test only. No other lens needs to re-run.

## Majors — fix now or file as scheduled follow-ups (all three verified)

### MAJ-1 — `versionAnchoredDate` bakes a fabricated, reader-visible `dcterms:modified` into every ePub, and its stated invariant is false

`src/doc-system/site/orchestrator.ts:370` (merged with the separate correctness-lens minor on monotonicity — same root cause).

The date is synthesised as `Date.UTC(2020,0,1) + major*365d + minor*1d + patch*1h`. Verified by execution:

| version         | produced               | note                                                                       |
| --------------- | ---------------------- | -------------------------------------------------------------------------- |
| `1.13.0`        | `2021-01-13T00:00:00Z` | ~5.6 years in the past; **already in the committed `docs/tosijs-ui.epub`** |
| `1.13.24`       | `2021-01-14T00:00:00Z` | **collides with 1.14.0**                                                   |
| `1.14.0`        | `2021-01-14T00:00:00Z` |                                                                            |
| `1.13.25`       | `2021-01-14T01:00:00Z` | **later than 1.14.0**                                                      |
| `2.0.0`         | `2021-12-31T00:00:00Z` | **earlier than 1.400.0**                                                   |
| `1.13.0-beta.1` | `2021-01-13T00:00:00Z` | collides with the final                                                    |

The docblock asserts the mapping "must be STABLE and monotonic" and "strictly increasing with the version". It is neither. The OPF carries **no `<dc:date>`**, so `dcterms:modified` is the only date a reader can surface. `SiteConfig.epub` (`site-config.ts:211-235`) exposes no `modified`, so adopters cannot override it — the 1.13.0 review proposed _either_ the version mapping _or_ an explicit `epub.modified`; only the first landed. No test asserts on `modified`.

**Fix:** add `epub.modified` (or a release-date field) to `SiteConfig`, falling back to the version-derived constant; use a non-wrapping encoding (`(major*1e6 + minor*1e3 + patch) * 60_000`); and fix or delete the monotonicity claim. Same pass: `epub.ts:511` still says the reader-visible date "IS set from the commit" and `orchestrator.ts:1311` still says "the commit time is the honest answer" — both now false.

Scope correction: `epub` defaults to false, so the blast radius is adopters who opt into ePub output, not literally every consumer. Still a published redistributable asserting verifiably false metadata.

### MAJ-2 — the #90 CSRF fix rests solely on `Sec-Fetch-Site` and allows the header's absence

`src/doc-system/site/dev-auth.ts:608`.

`isSameOriginRequest` returns true when `sec-fetch-site` is absent. The only other clause (`mode === 'no-cors' && site === null`) is dead in practice — no engine shipped `Sec-Fetch-Mode` without `Sec-Fetch-Site`. So a browser that sends no fetch metadata (Safari < 16.4, Firefox < 90, iOS WKWebView < 16.4) is in the **pre-fix position**: `handleWriteSource` (`dev-server.ts:918`) parses `request.json()` with no `Content-Type` check, and `resolveInRepo` (`:895`) accepts any path under the project root — `.git/hooks/pre-commit` included. Preconditions hold on a default setup (`editableSources: true` in this repo's own `tosijs-site.config.ts:50`, documented port, mkcert-trusted cert).

The review that prescribed this fix asked for `Sec-Fetch-Site` **OR** an `Origin` mismatch check. The `Origin` half was silently dropped — `grep` for `get('origin')` across `src/doc-system/site/` returns zero hits — and `Origin` is exactly what the affected browser population _does_ send.

Worst part: `dev-auth.test.ts:1010-1016` asserts absence-allows as intended and comments that "a browser always sends it". That is false for the population above, and it is what a future reader will use to decide _not_ to strengthen this. `CHANGELOG.md:71` repeats the claim.

**Fix:** refuse when `Origin` is present and does not match this server's origin (CLI/curl send none, so nothing legitimate breaks), and/or require `Content-Type: application/json` on these endpoints to force a preflight. If the residual is accepted instead, say so explicitly in `dev-auth.ts` **and** the CHANGELOG, and correct the test comment.

### MAJ-3 — the same-origin term is spliced in at two call sites, so `POST /report` kept no CSRF gate and the next endpoint inherits nothing

`src/doc-system/site/dev-server.ts:1881`.

`mayWriteSource` (`dev-auth.ts:621-631`) is unchanged peer-address-only; `isSameOriginRequest` is ANDed inline at exactly two sites (`:2020` `/__docstore/source`, `:2051` `/__build`). `POST /report` (`:1881-1892`) is gated only by `viaTunnel || !isLoopbackAddress(peer)` — verified in the source above — and `handleTestReport` parses JSON regardless of `Content-Type`, writes `.browser-tests.json`, and resolves `testReportResolve`. Its own comment describes the consequence: "a green exit code for a suite that never ran… it makes the gate lie." The most reproducible attacker is any _other_ page served from localhost, which sends `sec-fetch-site: same-site` — refused by `isSameOriginRequest`, accepted by `/report`.

The propagation cost is already realised, not predicted: `haltijaBridgeAllowed` (`:1064-1081`) reaches `mayWriteSource` and gets no CSRF gate either, on a path `dev-auth.ts:633-644` documents as "at least as powerful as writing source". And the tests assert `isSameOriginRequest` on synthetic header bags in isolation — the composed `viaTunnel || isSameOriginRequest(...)` rule is untested at **both** patched sites.

**Fix:** move the CSRF term inside the decision function (`mayWriteSource({ viaTunnel, peer, hasValidSession, sameOrigin })` or a shared `mayAcceptLocalWrite(request, srv, viaTunnel)`) and route `/__docstore/source`, `/__build` and `/report` through it. Test the composed rule.

Two overstatements in the original finding, neither changing substance: `mayWriteSource` is **not** re-exported from `tosijs-ui/site`, so "an adopter calls it" is wrong (only future in-repo endpoints do); and the CHANGELOG scopes its claim honestly to the two endpoints.
