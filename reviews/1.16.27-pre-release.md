## Fix before the tag

- [ ] **(major, confirmed, correctness) Re-running `--go` on a box where Caddy is down restores the broken file and blames the new config.** `bin/caddy-install.ts:173`. `systemctl reload caddy` exits non-zero on an inactive unit. The new branch then does `cp -p Caddyfile.bak Caddyfile`. On a 1.10.0–1.16.26 box, that .bak is the root-only file Caddy cannot read. The script prints "caddy refused the reload; restored the previous…" and exits 1. The bin then says "Nothing was installed". A box hit by 1.16.26 can therefore never recover through `--go`, which is the remedy the CHANGELOG gives. The same happens on any box with Caddy stopped, including a fresh install where Caddy is not yet started. This is a regression against 1.16.26, which left the correct new file in place.
  **Fix:** run `systemctl is-active --quiet caddy` before swapping. If Caddy is inactive, use `systemctl reload-or-restart caddy` (or `start`) and roll back only if that fails. The message should name "caddy is not running / failed to start" separately from "refused the config". Optionally decide whether to roll back with `caddy validate`/`adapt` instead of the reload's exit code.
  **Clears when:** a test whose systemctl stub reports inactive for `is-active` and fails `reload` ends with the NEW 640/644 file in place (and Caddy started), and that test fails with the fix reverted.
- [ ] **(minor, confirmed, blast-radius; same lines, fold in) The restore keeps the old root-only mode.** `bin/caddy-install.ts:175`. `cp -p` of a root-only .bak puts back the restart-time outage this release fixes, while reporting "restored". **Fix:** after restoring, re-apply the same chgrp/chmod as for the new file (or drop `-p` and set the mode explicitly). **Clears when:** a test seeds a 0600 old Caddyfile, forces a reload failure, and asserts the restored file is group-readable by caddy.
- [ ] **(minor, confirmed, security+docs, merged) The 644 fallback makes both keys world-readable.** `bin/caddy-install.ts:166-170`. With no `caddy:` line in /etc/group (Caddy run as root, under www-data, or with the group coming from NSS/LDAP), the file holding PREVIEW_TOKEN and PREVIEW_EDIT_TOKEN becomes 644. That contradicts the comment two lines above ("not world-readable either"). Before this diff, umask 077 kept it at 600. **Fix:** never fall back to world-readable. Look the group up with `getent group caddy`, or take it from `/etc/caddy/preview.env` or `systemctl show -p Group caddy`. If no group is found, use 600 (right for Caddy running as root) or refuse with a message. Bring the comment and the CHANGELOG into line with the choice. **Clears when:** the test asserts `mode & 0o004 === 0`, which fails on the current 644 branch.

These need no re-review.
