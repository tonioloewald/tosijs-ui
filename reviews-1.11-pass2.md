## 🛑 Blocker (1)

### B1 — `bun run release-check` exits 1, and the release commit claims it is green

**`CHANGELOG.md` · lens dx/docs · confirmed**

Reproduced verbatim:

```
🛑 1 annotation(s) since v1.10.2 are not mentioned in CHANGELOG.md:
   [new] filed tosijs-ui#102 … (a8687a75)
```

CLAUDE.md makes this step 3 of the Publishing checklist, and `a8687a75`'s own body asserts _"All 70 annotations since v1.10.2 are accounted for; `release-check` is green."_ That is false against the state it created. Shipping over a red gate is the pattern the tool exists to prevent, and it trains the next person to `|| true` past it.

There is a second trap here: `collect()` builds the range as `${since}..HEAD`, **exclusive** of the since-commit — so tagging `v1.11.0` at `a8687a75` empties the range and turns the gate green without the bullet ever being written. The annotation escapes permanently in both directions.

**Fix:** either write a one-line "Known issues" entry naming `#102` (the matcher is satisfied by mentioning the issue number), or re-tag the annotation `[note]` if filing an upstream issue is internal. Then correct the commit body's green claim. Re-run until exit 0 **before** tagging.

## ⚠️ Must fix before the tag (2 — not blockers, but they ship wrong to users)

### G1 — `tosijs-schema` 1.8.0 is live; our `^1.7.0` floor admits it, and our vendored workaround now lies

**`src/schema-form/unenforced.ts:27` · lens ecosystem · confirmed**

Verified: `npm view tosijs-schema dist-tags` → `latest: 1.8.0`, published today. 1.8.0 closes tosijs-schema#8 — its `ENFORCED_KEYWORDS` grew to 24 (adding `oneOf`, `exclusiveMinimum`, `exclusiveMaximum`), `validate` genuinely branches on all three, and it **exports `unenforcedKeywords`**, which was ask (3) of our own issue.

Our peer _and_ dev ranges are both `^1.7.0`, and `bun.lock` pins 1.7.0 — so CI is green today. Two consequences:

1. **A fresh adopter sees a false statement.** `^1.7.0` resolves to 1.8.0 on install. Open a `<tosi-schema-form>` over `{oneOf: […]}` or `{type:'number', exclusiveMinimum:0}` and every such field renders _"oneOf is not validated"_ while the validator is enforcing it. The note exists to stop the form lying about what it checked; under the current floor it is the thing lying, on the most common union spelling, in the release's headline component.
2. **Red unit lane on the next lock refresh.** `unenforced.test.ts:11` asserts strict set equality (21 local vs 24 upstream). `bun latest` (a documented command), a Dependabot bump, or any clean install turns it red.

Mitigating: the note errs _conservatively_ — it claims less checking than exists, so it cannot produce a green form over a forbidden value. That keeps it below blocker.

**Fix:** run `bun bin/verify-schema-dep.ts --version=1.8.0` and set the floor deliberately. Prefer the upstream export at runtime (use `unenforcedKeywords` from the registered validator when present, local walker only as fallback) so the note can never contradict the validator in use. Relax the parity test to `ENFORCED ⊆ ENFORCED_KEYWORDS` (still catches upstream _shrinking_, the dangerous direction). Note 1.8.0 also `console.warn`s once per process on `oneOf` — decide whether to call `setWarnings(false)`.

### G2 — CLAUDE.md:286, added by this release, states a false measurement

**`CLAUDE.md:286` · lens docs · verified during triage**

The new paragraph reads: _"**Measured 2026-08-24 and no longer true as written:** CodeMirror is NOT in `dist/iife.js`. `lezer` appears zero times…"_

sources total: 110   codemirror/lezer/code-editor-cm: 21
../node_modules/@codemirror/state/dist/index.js
../node_modules/@codemirror/view/dist/index.js
../node_modules/@lezer/common/dist/index.js

CodeMirror **is** in the iife, exactly as the pre-existing text (and the README) said. The measurement failed because `dist/iife.js` is minified — package paths and identifier names survive only in the sourcemap, so `grep -o lezer` returning 0 is not evidence of absence.

This is worse than an ordinary stale doc: the paragraph is in the file agents are told to read first, it _instructs_ the wrong measurement method, and it has already done damage — one review lens read it, filed a "the README is wrong" finding on its authority, and a skeptic had to spend a full verification pass refuting it. The paragraph also contradicts itself (it deletes a caveat, then says "don't repeat the claim without that caveat").

**Fix:** revert the false assertion, restore the accurate description, refresh only the number (409,603 B gzip / 1,312,688 B raw today vs the stale ~385KB), and record the correct method: _measure via `dist/iife.js.map` sources, never grep the minified bundle_. Better still, emit the figures from the size-reporting step `bin/dev.ts` already runs (see P-minor-3).
